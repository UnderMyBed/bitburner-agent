# Browser parity audit

The simulator runs the real game headless: Node, jsdom, a virtual clock, no React rendering ([architecture §9.1](../architecture.md#91-design), [ADR 0007](../decisions/0007-headless-engine-simulator.md)). But the game also relies on things a browser and its mounted UI provide without being asked. This page lists every such thing we found, and what the simulator does about each one.

- **Game version audited:** v3.0.1 (`vendor/bitburner-src` at `1da7316ff`). **Browser:** Electron 41.4.0, the one in its `package-lock.json`, with Chromium 146.0.7680.216; the timer model follows that Chromium (§8).
- **Citations:** `file:line` in the game's tree (`vendor/bitburner-src/`), unless the path starts with `packages/` (ours). Test files are in `packages/sim/test/`.
- **Dispositions:**
  - **handled**: the simulator reproduces it. The test that proves it is named; otherwise the row says why no test is needed, or which issue adds one.
  - **irrelevant**: no effect on game state or on what a script sees, or reachable only through UI clicks or terminal typing, which don't exist headless. The reason is given.
  - **gap**: it behaves differently headless, and it shouldn't. Each gap has an issue; the summary lists the open ones.
  - **by design**: a deliberate difference, documented where users of the simulator will see it.
- **Re-audit** whenever the pinned version moves: see [the checklist](#re-auditing-after-a-version-bump).

## Summary

The headless router (§2, [#28](https://github.com/UnderMyBed/bitburner-agent/issues/28)) and the page layer (§3, §4; [#47](https://github.com/UnderMyBed/bitburner-agent/issues/47)) close the gaps the first audit found. The last two, Node's globals reaching scripts (4.14, [#57](https://github.com/UnderMyBed/bitburner-agent/issues/57)) and script URLs containing one another (§8, [#58](https://github.com/UnderMyBed/bitburner-agent/issues/58)), are closed too. None remain open.

The by-design differences:
- **Saves and fixtures:** autosave is off (1.7); every new game chooses whether the tutorial runs (1.10); a save the game can't load fails the simulation's start instead of opening the Recovery page (2.3).
- **A simulated player at the UI:**
  - Prompt rules answer at once (3.1). A prompt no rule matches waits, as with nobody at the screen.
  - Error popups are closed at once, so every error is reported (3.11).
  - The event log keeps what the UI would drop: repeated alerts, and toasts on pages that hide messages (3.3, 3.5).
- **No windows; sockets only to the parent:** no tail windows and no real window size (3.8, 4.8). The simulator is offline, except for WebSockets to URLs the parent listens on, which cross in lockstep with the virtual clock (4.6, 4.15; [ADR 0012](../decisions/0012-simulator-network-in-lockstep.md)).
- **Globals:** the page's globals are shared between `window` and the global object, but a property a script adds to one later isn't on the other (4.4).
- **From §8:** no rendered UI, no TS/JSX player scripts, no script modules that await a timer at top level, compiled script modules are never dropped ([#73](https://github.com/UnderMyBed/bitburner-agent/issues/73)), and a 0 ms timer set while the clock is advancing waits 1 ms of virtual time ([#80](https://github.com/UnderMyBed/bitburner-agent/issues/80)).

The [simulator README](../../packages/sim/README.md#differences-from-a-browser) lists the ones that affect what scripts can do.

## 2. The Router (`src/ui/GameRoot.tsx`)

Game logic reads the current page and navigates. `GameRoot` builds the real Router when it renders (`GameRoot.tsx:246-291`); until then the game has a stub (`:119-150`). The stub always reports the loading screen, hides messages, and queues navigation with a console error. Headless nothing renders, so without the simulator's own router every page read would be wrong and every navigation dropped.

The simulator's headless router (`packages/sim/src/engine/bundle/router.ts`) takes over at the point `GameRoot` first renders. Page changes are synchronous, as in the real game. React 17's `ReactDOM.render` (`index.tsx:17`) re-renders synchronously when state is set outside React's batching (event handlers, `unstable_batchedUpdates`, render and effects), and that's how game logic and scripts navigate.

The router's page history is runtime state the save doesn't hold, so the state hash includes it (test: "the page is part of the state hash…"). The tests below are in `router.test.ts`, and each fails on the stub. "The copied router constants still match the game's GameRoot.tsx" fails if a version bump changes the history size or the message-hiding pages.

## 3. Dialogs, alerts, toasts, prompts and other emitters

The game's `EventEmitter.emit` calls subscribers synchronously and does nothing without any (`utils/EventEmitter.ts:13-21`). Most UI emitters have only React subscribers, so headless they're no-ops. What matters is whether game logic or a script waits on an answer. The simulator subscribes to the ones that show something, and reports them as sim events (`packages/sim/src/engine/bundle/page.ts`). A subscriber never throws back into the game: content it can't render is reported as such.
