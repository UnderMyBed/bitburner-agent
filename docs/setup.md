# Setup

How to run the agent against Bitburner on Steam, from a clone of this repository ([#95](https://github.com/UnderMyBed/bitburner-agent/issues/95), [#122](https://github.com/UnderMyBed/bitburner-agent/issues/122); architecture §10.1, §10.2). The brain runs from the repo, in a terminal, and is started again if it crashes. It launches the game, deploys the in-game Agent, and keeps both going while it runs.

**Nothing is installed.** There's no service, no scheduled task and no standalone binary (owner decision 30). Everything the brain writes goes in the repo's gitignored `.data/`: its config (with the control channel's token), the store, the in-game build and the save backups, unless you give it another data directory (below). npm's own download cache is the one exception. To stop it, stop the brain. To remove it, delete the clone, after copying out any save backups in `.data/saves/` you want to keep.

**You run these steps yourself.** They act on your game. Claude builds the agent but never drives your game or your system.

## Before you start

- Windows, with Steam and Bitburner installed (Steam app 1812820).
- [Node.js 26](https://nodejs.org/) and git. The brain runs on 26 or later; the simulator's scripts need 26 itself (below). The pin moved from 24 to 26 after 1.0.1 ([#301](https://github.com/UnderMyBed/bitburner-agent/issues/301)). `v1.0.1` and earlier pin 24 in `.node-version` only, with no `mise.toml`, so mise gives them your global Node there; set `MISE_NODE_VERSION=24` to run one on 24.
- **Which Node runs in the clone.** The repo pins Node 26 in `.node-version`, which CI follows. If you use [mise](https://mise.jdx.dev/), the repo's `mise.toml` selects Node 26 inside the clone, with no global change: mise doesn't read `.node-version` by default, so without it your global mise Node would run here. Check with `node --version` in the clone. On the reference machine mise used it without a `mise trust`; if mise asks for one, run `mise trust` in the clone. If mise doesn't have a Node 26 yet, `mise install node@26` adds one to mise's own folder. A `MISE_NODE_VERSION` you set still overrides the repo's choice. The simulator's scripts (`npm run sim`, the baseline and the bench) refuse any other major, exiting 2 with what to do: seeded games differ between Node majors ([#282](https://github.com/UnderMyBed/bitburner-agent/issues/282)). Node 26's V8 should be the one in Steam's Electron, so on 26 they sort as Steam's game does.
- **One brain, one game.** The brain serves one game on the fixed ports 12525–12527: run one brain at a time, and don't point a second game at it.

## 1. Clone and bootstrap

Only tagged releases go to Steam (architecture §6). Clone the repository and check out the newest release tag. `v1.0.0` is the example below (`v0.2.0` was the first with these steps).

For a release's live run on Steam ([releasing](releasing.md) step 2), check out the candidate commit instead. It's recorded on the milestone's review issue. Then follow [this page as it is on `main`](https://github.com/UnderMyBed/bitburner-agent/blob/main/docs/setup.md), not the copy in your checkout: docs fixed after the candidate are only there.

**Already have a clone?** Use it. Stop its brain if it's running, then follow [Upgrading to a new release](#upgrading-to-a-new-release) with the tag or commit you want. That ends with step 2's `npm run brain`, so carry on at step 3. Its `.data/`, if it has one, carries over: the config, the store and the save backups.

```
git clone https://github.com/UnderMyBed/bitburner-agent.git
cd bitburner-agent
git checkout v1.0.0
npm run bootstrap
```

`npm run bootstrap` fetches the game's source (the `vendor/bitburner-src` submodule), installs this repository's packages, then the game's own dependencies. It says each step, stops at the first that fails, and can be run again. The brain needs the submodule: it checks the game's version against it, and stops at start if it's missing.

## 2. Start the brain

```
npm run brain
```

It runs in that terminal until you stop it (Ctrl+C) or close the terminal.
- **If the brain crashes, it's started again** after 5 s, then 10, 30 and 60 s if it keeps crashing; a run of 5 minutes or more starts that over. Each restart is a `brain runner:` line.
- **After a reboot**, run `npm run brain` again: nothing is installed to do it for you.

**What happens next.** The brain:
- builds the in-game code (a few seconds);
- creates `.data/config.json` in the repo, the first time;
- serves the dashboard at **http://127.0.0.1:12527/**;
- **launches Bitburner through Steam about 30 s later**.

The brain's output is its log: deploys, connections, save backups, errors. If it stops at start, the last lines say why. A `config.json` it doesn't accept names the field and what it should be.

**A config from an earlier brain** may lack fields added since: `saveBackupIntervalMinutes`, `saveBackupsKept`, `steamAppId`, `gameExecutable`. Add them with their defaults ([the brain's README](../packages/brain/README.md#the-data-directory)), or move `.data/` aside and start fresh. A config from v1.0.0 needs nothing added: `telemetryKeptWholeDays` is optional, and absent means no thinning at the start (below).

## 3. Pause supervision while you set up

**Wait for the game to open, then open http://127.0.0.1:12527/ and click "Pause supervision".** If it has been more than a minute and the game hasn't opened, start it from Steam yourself. While supervision runs, the brain kills and relaunches a game that has no Agent reporting for about 5 minutes. Until you've finished step 4, no Agent reports.

An `agentSilent` alert is expected until step 4.4.

## 4. Set the game up

1. **A brand-new save:** click "Exit Tutorial" first, in the tutorial's panel. While the tutorial runs, the game's terminal runs only the tutorial's commands, so step 4.4's `run agent/boot.js` would be refused, and the agent can't end it for you ([architecture §5.7](architecture.md#57-bootstrap-and-restart-c5)).
2. **Options → Remote API:**
   - Hostname `127.0.0.1` (not the default `localhost`: the brain listens on 127.0.0.1 only);
   - Port `12525`;
   - Reconnection delay `5` (above 0, so the game reconnects when the brain restarts);
   - "Use wss" off;
   - then click **Connect**. Changing the settings alone doesn't connect.

   The dashboard's **Recent events** should show `deployed` (or `deploymentCurrent`) and a `saveBackup` within a few seconds.

   **If it doesn't connect** and the dashboard's events show `connectionRejected`, the game's page sent an origin the brain doesn't allow. The brain allows `file://`, Steam's page, by default.
   - Copy the origin from the event, without the ` (Remote File API)` the brain adds after it, into `allowedOrigins` in `.data/config.json`. Never add `(none)`: that's a connection with no origin at all, not a page.
   - Then restart the brain: Ctrl+C, and `npm run brain` again.
3. **Options → System:** set "Autoexec Script + Args" to `agent/boot.js`. Autoexec runs on every load of a saved game, so after this the Agent starts by itself.
4. **First start of the Agent:** in the game's terminal, type `run agent/boot.js` once. Autoexec can't do this first start: it ran when the game loaded, before the brain had deployed.

   The dashboard's **Agent** table shows "Connected: yes" with the deployment, and the tiers start arriving.
5. **Save the game** (Options → Save Game), or wait for an autosave. The game keeps its settings in the save, so settings changed after the last save are lost if the game is relaunched.

## 5. Resume supervision

Click **"Resume supervision"**. From now on, while the brain runs, it relaunches the game if it closes, or if the Agent goes silent for 5 minutes. It does so at most 3 times an hour; after that it stops and shows an alert.

The skeleton now runs as long as the brain does. After a reboot, run `npm run brain` again: the brain launches the game, and autoexec starts the Agent.

## Day to day

- **The hack loop** (since v0.3.0) is on by default (owner decision 34). Once the Agent connects, it roots the servers it can and runs a loop on the game's servers against the target the brain picks; the dashboard's "Hack loop" line names it. When a better target comes within reach, the largest servers prepare it while the rest keep earning, and the line names that too ("preparing zer0 on 7 servers"); all move to it once it's ready. Each server hacks with only so many threads that, together, they never take more of a target's money than it grows back quickly, so money keeps rising: the line says how many ("hacking with at most 48 threads", #187). It never runs on home, your Hacknet servers or your own cloud servers, only the game's servers and the brain's own cloud servers (#194), and it never touches your own scripts ([the hack loop](../packages/ingame/README.md#the-hack-loop)).
  - **With the batcher on** (its default since #206), the batcher hacks from these servers instead and the hack loop only roots; switch the batcher off and the loops come back.
  - **It fills the free RAM** on the servers it runs on, so a script you start there later may not fit. A loop you kill comes back within about 30 s. To use those servers yourself, stop the loop first.
  - **Money flat for 10 minutes** with the loop on is the dashboard's `incomeStalled` alert, with how long, the money and the target, and a line in the brain's window as it starts and ends. A purchase lowers money, which doesn't count as a rise. It shouldn't happen: if it does, `npm run report` names the stall, and it's worth an issue.
  - **To stop it,** click **"Stop the hack loop"** on the dashboard: every loop stops within a few seconds, and it stays off, across brain restarts, until you start it again.
- **The batcher** (since v1.0.0) is on by default (#206, [owner decision 49](decisions/owner-decisions.md)), with the hack loop on: the brain hands the hack loop's servers to the batcher instead, and the hack loop still roots. It runs from home once home has 16 GB, or from your largest rooted server, and hacks in batches (hack, weaken, grow, weaken, each landing in order). **The brain picks its target:** the one worth most over the next 15 minutes, counting the time to prepare it, so it starts on n00dles. A richer server is prepared as the next one, on the RAM the batches leave (a fifth at least), and it moves there once that server is ready (#236), so a move costs a couple of minutes without a hack at most. Its share and spacing follow your hacking level as it rises. In the simulator it earns 1.41 to 1.82 times what the hack loop does on A1's measure (about 30% of the best a batcher could earn on your servers, against the hack loop's 16 to 20%), and far more money. The dashboard's "Batcher" lines say where it runs and against what, and its health: batches, hacks, and any desync (a landing out of order, or the target's money or security outside what a batch in step leaves), which it recovers from by itself; a desync, a late or lost operation, or a problem shows red, the dashboard's `batcherOutOfStep` alert says so, and the run report fails the run, unless a page stall (or, for a batcher before #251, a clock step) explains it and the batcher recovered by itself (a warning, #241). The brain's window logs each change of target, of the next target, and of mode (the hack loop takes over when no server holds the batcher). If it can't start (no room on its server, say), the Agent tries again within seconds; still down after 3 snapshots, the dashboard's `batcherNotRunning` alert says why, and the run report fails, since nothing hacks the servers the hack loop left to it. **"Stop the batcher"** stops it within a few seconds and the hack loop takes its servers back; it stays off across brain restarts until you start it again ([the batcher](../packages/brain/README.md#the-batcher)).
- **Sharing spare RAM** (since v1.0.0, #224, on by default, [owner decision 52](decisions/owner-decisions.md)): while you work for a faction (work set on the dashboard, or the brain's; work you start by hand in the game isn't seen), the batcher shares the RAM its batches leave, and home's above 32 GB, with `ns.share()`, which raises the reputation faction work earns: about 1.6 times for hacking work on the 26 PB of the first overnight run (field and security work gain less: only their hacking and intelligence part is raised). Batches always come first: it keeps their peak RAM, a quarter more, and the next target's free, never takes the batcher's servers past 80% in use (home isn't counted), and starts a round every 5 s at most, each lasting 10 s, on half of what it may share, so as one round ends the other still shares (#242). Home shares whenever you work for a faction, whatever the batches are doing. Early on, when the batches need all the RAM, it shares nothing. With the batcher off, nothing shares. The dashboard's "Batcher" lines show its threads, RAM and bonus, and the "Sharing spare RAM" section why it isn't asked while it's on; the run report says how long it shared and at what bonus, and fails if a batch came up short of RAM, or was planned smaller for the share's threads, while it shared on the batcher's servers (a short while only home shares is the batcher's own, `batches short of RAM` below, #230), or if it was asked, had room, and shared nothing for 10 minutes, or, while asked, left over half of what home may share (its RAM beyond what it keeps) free for 5 minutes (#242). It also shows the bonus on average while asked against the bonus possible under the share's rules, and the time at no bonus. With Singularity (BN4 or SF4), home keeps 32 GB plus the most its largest Singularity worker takes at your SF4 level, not all of home. **"Stop sharing spare RAM"** stops new rounds at once; the last ends within 10 s (work you stop by hand, within about 40 s) ([sharing spare RAM](../packages/brain/README.md#sharing-spare-ram)).
- **Buying the hacking programs** (since v0.3.0) is on by default too. When you can afford the next one, the Agent buys the TOR router at your city's tech vendor, then BruteSSH.exe, FTPCrack.exe, relaySMTP.exe, HTTPWorm.exe and SQLInject.exe through the terminal, so the hack loop can root more servers ([the hacking programs](../packages/ingame/README.md#the-hacking-programs)).
  - **It uses the game's page, as you would:** a few times a session you'll see the page switch to the City and back, or a `buy` typed into the terminal. However it goes, it ends on the Terminal, or, if you were focused on work, focused on it again.
  - **Keep the sidebar's Hacking, Character and World sections open:** they hold the Terminal, Factions, City and Job. With one collapsed, what goes through it (buying, joining a faction, buying an augmentation, starting work at a faction or a company) waits until it's open again.
  - **The faction state** (since v1.0.0, #197): to read each faction's reputation and favour, the invitations and the augmentations bought but not installed, the Agent opens the Factions page (and the Augmentations page while anything is queued) when it starts, and after that only when something there may have changed (a faction joined, an invitation, a purchase, an install) or every 10 minutes while you've joined a faction or have an invitation. In between it reads the reputation of the faction you work for from the page as it is, and nothing moves. After a read it puts the page back as it found it: your work focused again, or the page you were on (a location's page goes back to the City map, and a faction's augmentations to the Terminal). It never reads while the casino is open: leaving mid-hand would forfeit your bet. The reputation of factions you aren't working for may be up to 10 minutes old. Opening Factions clears the sidebar's badge for new invitations, as looking yourself does, and the invitation's dialog is answered "Decide later" for you (#143), so **the dashboard's Factions section is where a new invitation shows**. If it can't be read, the section says why; 3 minutes of that in a row raise the `factionStateUnread` alert, and the run report fails. With Singularity (SF4) and room on home, none of this touches the page.
  - **The game's own dialogs are handled for you** (owner decision 35): the Agent closes the game's alerts ("Offline for…" after a load, purchase and travel notices), and answers a faction invitation with "Decide later", so it waits on the Factions page. What each said is on the dashboard's recent events (`gameDialog`). Any other dialog (a script's `ns.prompt` or `ns.alert`, or one you opened) is yours: nothing is done on the page while it's open, and the dashboard's `dialogBlocking` alert quotes it. Nothing is typed into the terminal while you've a line typed there either.
  - **Chongqing and New Tokyo have no tech vendor:** in either, the TOR router waits until you travel, and the dashboard says so.
  - **Nothing is bought while the brain holds** (after a Steam update, a failed deploy, or a game version it wasn't built for).
  - **To stop it,** click **"Stop buying programs"** on the dashboard; **"Start buying programs"** turns it back on.
- **Upgrading home's RAM** (since v0.3.0) is on by default too. When you can afford it, the Agent doubles home's RAM at your city's tech vendor, the same way: the page switches to the City and back to the Terminal once per upgrade ([home RAM](../packages/ingame/README.md#home-ram)).
  - **One purchase at a time, the cheaper first:** with buying programs on too, the upgrades and the programs take turns by price (16 GB comes after BruteSSH.exe and before FTPCrack.exe), and the dashboard says which one waits for which. So while an upgrade can't be made (World collapsed), the next program waits for it too.
  - **BN1 only, for now:** other BitNodes change the price, so there it waits, and the dashboard says so.
  - The same as for the programs: keep the World section open, close your own dialogs (and your scripts'), travel from Chongqing or New Tokyo, and nothing while the brain holds.
  - **To stop it,** click **"Stop upgrading home RAM"** on the dashboard; **"Start upgrading home RAM"** turns it back on.
- **Buying cloud servers** (since v1.0.0, #194) is on by default too. The brain buys cloud servers (`pserv-0`, `pserv-1`, …) through the NS API, with nothing on the page, and the hack loop runs on them. Your own cloud servers, under any other name, are left to you: the loop never runs on them and the brain never upgrades them, but they count toward the game's limit of 25 ([cloud servers](../packages/brain/README.md#cloud-servers)).
  - **When:** once the hack loop has earned for 10 minutes, it measures what a GB of its servers earns a second, and buys the largest server money allows if it pays for itself within 15 minutes at that rate. That comes once the loop has moved past n00dles to a richer target: in the simulator, 80 to 100 minutes into a fresh start. At the game's limit of 25, it upgrades its smallest instead. BN1 only, for now.
  - **After the programs and home RAM:** one purchase at a time, those first. While the next program or home RAM upgrade waits for money, and the income would bring what's short within a minute, that money is kept for it.
  - **The dashboard's Cloud servers section** says what it's buying, for how much and how soon it pays back, or what it waits for, and lists your cloud servers.
  - **If a purchase goes wrong** (bought under another name), the `cloudServerProblem` alert says so and it buys no more: look at the alert, then turn it off and on again. A restarted brain forgets the hold, but the run report still fails on that purchase.
  - **To stop it,** click **"Stop buying cloud servers"**; **"Start buying cloud servers"** turns it back on.
- **Backdoors for the hacker factions** (since v1.0.0): once the hack loop has rooted CSEC and your hacking level reaches its requirement (51 to 60, depending on the game), the brain has the Agent backdoor it, so CyberSec invites you; then avmnite-02h (NiteSec, about level 210), I.I.I.I (The Black Hand, about 350) and run4theh111z (BitRunners, about 530), one at a time ([backdoors](../packages/brain/README.md#backdoors-for-the-hacker-factions)). You'll see `home`, a few `connect`s and `backdoor` typed into the terminal, a few seconds' wait, and `home` again; if you were focused on work, it's unfocused for that and focused again after. The invitation's dialog is answered "Decide later", as for any invitation; the brain then joins it (below). The brain's window says "backdoor: asking for CSEC …" and "backdoor: CSEC backdoored …". There's no switch: a backdoor costs nothing. After an install the game removes them, and they're done again. If one is due for 5 minutes without being done, the dashboard's `backdoorOverdue` alert says so, and the run report fails ("backdoor overdue"); one that fails raises "intent stuck" after 5 tries, like any intent.
- **Doing something once** (since v0.3.0): the dashboard's **Intents** section queues a one-shot action, the action and its arguments as JSON, for example `travel` with `{"city": "Aevum"}`. The Agent does it through the game's page, as for the purchases, and it leaves the queue once the Agent reports it done; **Cancel** takes it off sooner. The queue holds 95. The section also lists the purchases, the backdoors, the joins, the travels for invitations (#228) and the augmentations the brain sends, and how each went. Anything can be queued, with no confirmation (owner decision 36), so check the arguments: a travel costs $200k. Joining one of the six city factions (`joinFaction`) can't be undone, since it bans the faction's enemies, so the brain holds it until two snapshots show it's still allowed and a save backup has been taken; the section says what it's waiting for. `purchaseAugmentation` takes `{"faction": "CyberSec", "augmentation": "Neurotrainer I", "level": 1}`; for NeuroFlux Governor, `level` is the level to buy next. `installAugmentations` takes `{}` and installs every augmentation you've bought, which resets the game: like a city faction's join, it waits for two snapshots and a save backup, and also until everything queued before it is done; whatever you queue after it waits until it's done, for the game after the reset. With Singularity (SF4), where its worker fits home beside the Agent (16 GB or more at SF4.3), the game starts the Agent again itself. Otherwise it goes through the page: you'll see the Augmentations page, the install's confirmation and alert, then `run /agent/boot.js` typed into the terminal, which brings the Agent back. A line you've left typed in the terminal is never typed over: then the game saves and reloads instead (through Options' "Force kill all active scripts"), and autoexec brings the Agent back. Keep the sidebar's Character and Help sections open: they hold Augmentations and Options. `buyServer` takes `{"hostname": "pserv-0", "ram": 8}`: a cloud server (8 GB costs $440k in BN1), bought with the game's API, not the page. A name one of the player's cloud servers already has is done without buying, and one of the game's own servers (`n00dles`, `home`, `w0r1d_d43m0n`) is refused. `upgradeServer` takes `{"hostname": "pserv-0", "ram": 64}` (#194): one of your cloud servers raised to that RAM, at the difference between the two sizes' prices ($3.08m from 8 GB to 64 GB in BN1), also with the game's API; already that big, it's done without paying, and a server that isn't one of your cloud servers is refused. `backdoor` takes `{"hostname": "CSEC"}`: the Agent types `home`, a `connect` for each hop and `backdoor` into the terminal, and goes back `home` once it's installed. The server needs root and your hacking level; the intent says which is missing. A backdoor takes a quarter of the server's hacking time, and the terminal is busy meanwhile: a purchase that types `buy` waits ("terminal busy") and is tried again 30 s later. A backdoor longer than about 2 minutes may raise the "intent stuck" alert until it ends, for itself and for a purchase waiting behind it. `w0r1d_d43m0n` is refused: its backdoor ends the BitNode, which is `destroyBitNode`'s. `destroyBitNode` takes `{"nextBitNode": 2}` (1 to 15): it destroys the BitNode and enters that one, which resets the game more than an install does (no augmentations, a new BitNode, the Source-File raised below the cap). Like an install it waits for two snapshots, a save backup and everything queued before it, and holds what's queued after it for the next BitNode; it also waits, saying which, for The Red Pill installed, root on `w0r1d_d43m0n` and your hacking level at its requirement. With Singularity, where its 33.9 GB worker fits home beside the Agent (a 64 GB home at SF4.3), the game starts the Agent again in the next BitNode. Otherwise it goes through the page: you'll see the terminal's `connect`s and `backdoor`, the BitVerse's cinematic and map, the next BitNode's portal and its "Enter", then `run /agent/boot.js` typed into the terminal, and the Agent closing the Source-File's dialog. A line you've left in the terminal makes it save and reload instead, as for an install (keep the sidebar's Help section open: Options is there). If the BitVerse's portal or the next BitNode's Terminal never comes, it gives up rather than reload from a page with no sidebar: the brain's supervisor relaunches the silent game, or you can reload yourself; the brain counts the destroy only once the game shows it. An intent tried 5 times without success raises an "intent stuck" alert with its last problem ([intents](../packages/brain/README.md#intents)).
- **Factions and their work** (since v1.0.0): the brain joins every faction that invites you. Of the six city factions (Sector-12, Aevum, …), whose join bans others until the next install, it chooses one group a cycle itself (owner decision 54, #228): Sector-12 and Aevum, or Chongqing, New Tokyo and Ishima, or Volhaven, the one with the most it would install that the money's invitations can earn. It travels to their cities for the invitations (you'll see the travel; $200k each), holds the money each invitation needs there ($15m to $50m) from cloud servers, home RAM and programs until it shows, joins them, and ends in a city with a tech vendor. The others' invitations it passes over; the dashboard's **Factions** section says which group and why ("City factions: group B (Chongqing, New Tokyo, Ishima): 5 augmentations that count, against A 4, C 3"). No travel while you've set work (a class or a job is in a city), queued a travel yourself, turned Augmentations off, or while an install is under way (but from Chongqing or New Tokyo, where home RAM isn't sold, it goes to Ishima first). An invitation not shown 5 minutes into a hold with the money is logged "NOT INVITED", and the run report fails. With no work set by you, it then works for the faction and work type that reach the augmentation with the most hacking value per second of work, by the game's own formulas: hacking work for CyberSec, for Neurotrainer I first, then the next ([factions and their work](../packages/brain/README.md#factions-and-their-work)). The **Factions** section says what it chose and why ("hacking for CyberSec, for Neurotrainer I (reputation 2 of 1,000, 0.32/s: about 52 min)"), and the **Work** row says "The brain's: …". The work is focused (decision 37), as yours would be, so the game shows the Work page; the hack loop carries on. If its faction's reputation rises under half the work's rate over 10 minutes, the dashboard's `factionWorkStalled` alert says so, the brain logs "faction work STALLED", and the run report fails; a join that fails raises "intent stuck" after 5 tries.
- **Augmentations and the reset** (since v1.0.0; owner decision 48): **a live run buys augmentations and installs them on its own, which resets the game.** It's on by default; the dashboard's **"Stop buying and installing augmentations"** turns it off ([augmentations and the reset](../packages/brain/README.md#augmentations-and-the-reset)).
  - **What it buys:** augmentations with a hacking, hacking speed, money, growth, chance or exp multiplier, or a faction reputation one, from a faction you've joined whose reputation already covers it, or (#225) whose donations are unlocked, with the money for a donation for the reputation it's short of. Not combat or charisma ones, until Daedalus's count (#228): short of 30 installed, any but NeuroFlux Governor and The Red Pill. The Red Pill only as below. The most valuable the money covers, dear ones early (a cheap prerequisite of a dear one with it), since each purchase makes the next 1.9 times dearer.
  - **When** (owner decision 51, the legacy scripts' rule): once it can afford 8 new augmentations, or 12 counting NeuroFlux Governor levels. Each number falls by one for every 2 hours the game has been running since the last install (the time the brain saw it online, not while it was closed), never below 1. In the first 20 minutes after an install, 4 counting NeuroFlux Governor's levels are enough (a quick install). It also installs when nothing more worth having is left at the factions you've joined. Until 30 are installed (Daedalus's count, NeuroFlux Governor's levels counting once), any augmentation is worth having (#228): those with a hacking value first, then the cheapest, and the dashboard's progress says "short of Daedalus's count"; with none of hacking value left to work for, the faction work goes to the soonest of the rest, "for Daedalus's count". An install while short that adds none to the 30 (NeuroFlux Governor's levels count once) is the `worldDaemonStalled` alert, and the run report fails ("Daedalus count stuck"); the World Daemon's line says how many more are within reach, and where. ## Upgrading to a new release

Stop the brain, then:

```
git fetch --tags
git checkout v1.0.0                 # or the candidate commit, for a live run
npm run bootstrap
npm run brain
```

The brain builds the new in-game code at start and deploys it when the game connects. The running Agent hands over to the new one by itself. Release notes say if `config.json` needs new fields.

## After a run: the run report

After a live run (or during one), `npm run report` says what the run did and what went wrong, from the brain's store alone, so nobody has to dig through SQLite by hand (owner decision 45). It reads; it never changes anything, so it's safe while the brain runs.

```
npm run report                                                  # from the newest brain start to now
npm run report -- --since 2026-10-28T21:26:00Z --until 2026-10-28T22:40:00Z
npm run report -- --verbose                                     # every intent, purchase, dialog and choice
```

**By default it summarises** what a long run does thousands of times (#245; run #3's 12.4 hours was 3,237 lines, most of them one intent, cloud server or augmentation each): section 3's intents, cloud servers, work, dialogs, faction work, invitations and augmentations, a line a cycle, and section 2's hack loop target, so the failures, the batcher and the path to the World Daemon stand out, and the report fits one GitHub comment. `--verbose` lists each line instead. Either way the checks (sections 4 to 6), every failure and warning line and the verdict are the same.

Times need a `Z` or an offset. **The default window starts at the brain's newest start,** which includes the brain runner's own restart after a crash: the part of the run before it is left out, and the rest can PASS on its own. Section 1 notes an earlier brain start in the day before the window. For a run that spans a restart, give `--since` the run's start.

It prints seven sections (1, 2, 2b, then 3 to 6), then a verdict:

1. **The window:** the brain's starts, the game's relaunches, the deploys and failed deploys, version drift, the Agent's connections and disconnections (with each session's deployment), the save backups and their failures, and the supervisor's failed checks and give-ups, in order. The data backups (#284), and those that failed, are listed and counted. A thinning of the store (#283) at this brain's start, or one that failed, and the data backup taken before it, are listed too, "(before the window)". Augmentation cycles** (#244): first a summary, one line a cycle (its start, length, how it ended, Daedalus's count before → after, and what held most of its time back); then one block per cycle, from an install to the next reset, a BitNode at a time. Out of step (a desync, or an operation late or lost) fails the run (#206), each stretch with its counts, its target and when it was first seen, **unless a page stall (or, for a batcher before #251, a clock step) explains it** (#241, [owner decision 55](decisions/owner-decisions.md)): its first look out of step seen from the incident's start (the game's clock's move, for a step) to a weaken's time on its target after its end, the batcher batching again by itself within 10 minutes of it, and nothing out of step in the 10 minutes after that. That's a warning naming it ("batcher out of step after a clock step: 1615 desyncs … after a clock step of +2.7 s from … (within a weaken there, …); recovered in … : batching again at …, and nothing out of step in the 10 min after"), not a failure: before #251 the batcher judged landings by the PC's clock, so a step made every part in flight look late, and it did what it should. Since #251 it times them on the page's monotonic clock, which no step moves, so a clock step explains nothing of a batcher since (its health's `clock` says which): out of step after one is a failure, put down to no incident. A page stall still explains it. If its run's looks end before that can be seen (the window ends; the batcher restarts; an install or a destroy resets the game), it's a warning too, "recovery not yet confirmed", as run #3's was ("batcher out of step after a clock step, recovery not yet confirmed: 1615 desyncs … recovered in 1 min 34 s: batching again at …, but its run's last look … (10 min needed)"). Otherwise it fails, saying why: no incident before it, none within a weaken there, one already put down to an earlier stretch, a weaken's time there unknown, not batching again within 10 minutes, or out of step again within 10 minutes. **A batch short of RAM fails the run too** (`batches short of RAM`, #232): the batcher plans each batch only as large as its servers' RAM holds beside everything else it runs there, so a short one (its hack lost) means something took that RAM after it was planned, such as a script of your own on the batcher's servers, RAM freed later than the 100 ms an operation waits for it (#246: a landing running late on a busy page), or a bug. Each short is listed with what held the RAM then: the batcher's own operations past their landing (RAM a busy page freed late), scripts not its own, or its share threads, and how late the landings then ran. An operation that finds no room first waits up to 100 ms for it, still in time; the report counts those waits and lists the last few with what held the RAM, so RAM freed late shows even when no batch is short. **An order that found its batch gone fails the run too** (`batch orders dropped`, #253): its batch's hack went out before it, so the hack landed without that grow or weaken. Since #253 the hack is always the last of its batch out, so this would be a bug. **A batcher stuck on poor targets is a warning for an hour, and a failure for 2 hours in a cycle** (`batcher stuck on a poor target`, #275): a target is poor while the best target you've rooted would earn 100 times more on the brain's hacking servers, each worked out from the game's formulas and capped by what the target's money can give (n00dles can't pay more than about $20m/s however much RAM you have). An hour or more on poor targets is a warning; 2 hours in all in one cycle, however it's split, is a failure. Stepping off a poor target for under 10 minutes doesn't end a stretch (its time isn't counted); 10 minutes or more does, and so does an install. The line names the targets, the cycle, the best target, how many times more it would earn (the range over the stretch, and the incomes at the largest) and your hacking level. The BN1.3 run spent about 5 hours on n00dles and phantasy at hacking about 1,000 to 1,600, and its report said PASS; the report would now name it. The thresholds are [owner decision 59](decisions/owner-decisions.md) (#275). Trimmed batches (fewer hack threads than the plan's, or none that time, while an older plan's batches still land) are shown, not a failure; those the share made smaller are shown apart, and fail as the share's. The money after each batch's grow (#234) is shown too: "full at all N looks", or how many found the target below its maximum, with the run's least so far and its target, a grow short of the hack before it (the batches then drift toward the floor that is a desync); and the grows it couldn't look at (something else landed on the target first, or a desync's recovery). Shown, not a failure. The batcher sent but not running for 3 fast snapshots in a row or more is a failure.

**The verdict** is `PASS`; `WARN` and one `warning:` line each when nothing failed but something went wrong that isn't yet a failure: something outside the brain that was put right by itself (#241: the batcher out of step after a page stall, or for a batcher before #251 a clock step, batching again, or not yet seen to), or the batcher an hour or more on poor targets, short of 2 hours in the cycle (#275); or `FAIL` and one line per failure from sections 4 to 6, then any warnings. A release needs PASS, or WARN with each warning explained on the review issue ([releasing](releasing.md)). It exits 0 on PASS or WARN, 1 on FAIL, and 2 when it couldn't run (no store, no brain start to begin from, a window that ends before it starts, or nothing recorded in the window). **On a FAIL,** each line has its times: look at that stretch in section 1 (what the brain and the Agent did then) and section 3 (what the Agent was trying; `--verbose` lists each intent with its times), and at the brain's terminal for those times. An income stall usually means the hack loop's target changed or the loop stopped: section 2's target line shows which. Put the report's output on the issue for the run ([packages/brain](../packages/brain/README.md#the-run-report)). **A PASS** means nothing in sections 4 and 5 went wrong while something was recorded. Silence after the run's last record isn't counted (the run stopping looks the same), so an Agent that hung with its connection still open would show only as the heartbeat line's time from the last record to the window's end.

## The campaign report

`npm run campaign` is the campaign's scoreboard: every BitNode in the store, across every run and brain restart, with how long it took to destroy, its cycles and installs, and which release played it (#290). It's what the releases are judged on ("did v1.0.1 clear BN1.4 faster than v1.0.0?"). Like the run report it only reads, so it's safe while the brain runs.

```
npm run campaign
```

It prints:
- **A row per BitNode** ("BN1.2": the number and level; "BN1.4 #2" for one played again): its start, how it ended, the time to its end by the clock and **online** (the game and the brain both up), the time **left out** of that (the game closed, or the brain or the Agent away for over 3 minutes: the game goes on offline, so this says how much of a clear wasn't watched), the cycles, the installs (and how many **by hand**: from your queue, the game's Install button or a Soft Reset, not the brain's own rule), the augmentations installed, the brain starts, and the releases. "≥" marks what's at least that: a BitNode begun before the store's first record or reached by loading a save, or whose first look showed an install already. Under it, each BitNode's Source-Files as entered, its time online by release, its augmentations by name, and any save loaded in it.
- **How a BitNode ended:**
  - **destroyed**: its Source-File went up a level, or at the Source-File's cap (level 3) the brain sent the destroy just before; with its Source-File overridden in the BitNode's options, the brain's destroy says it, else it's **unknown**;
  - **destroyed, BitNodes unseen**: its Source-File went up more than a level, or another one rose too, so BitNodes were played that the store didn't see (never a clear of its own); **BitNodes unseen** where only another rose;
  - **a save loaded**: the next BitNode's start is before this one's last look, so a save was loaded, older or newer (never counted as a destroy);
  - **a new game**: a Source-File was lost, or there was none (b1t_flum3 needs one);
  - **b1t_flum3**: another BitNode with no Source-File gained (at the cap, it could also be a destroy you did by hand);
  - for the newest BitNode, **destroy sent**, the next BitNode not seen yet, or **not yet**.
- **A row per release and BitNode it played:** its time online there, its cycles and installs, and whether it destroyed it. "A clear of its own" is a BitNode one release played from its start to its destroy, with no install by hand and no save loaded in it ("yes, with a save loaded in it" otherwise): the fair comparison. Another release that played only its first 5 minutes or less, with no install (a brain upgraded just after a destroy), doesn't stop it; its share is printed beside the clear (owner decision 61).
- **Compared:** each BitNode two releases or more cleared on their own, the fastest online first, with each clear's time left out and the Source-Files it was entered with.

A release is the brain's version (`git describe`, "v1.0.1"), whatever the Agent's build. Upgrading mid-BitNode splits its time between the two releases, so neither has a clear of its own there. Running the brain from an untagged or changed checkout makes every commit its own release ("v1.0.0-4-gabc1234"), so a clear to compare is a tagged release's.

It exits 0 with the report, and 2 when it couldn't run: no store, or no BitNode in it.

**The dashboard's "BitNodes and installs"** (#285) shows the same campaign while the brain runs: each BitNode, the newest first, with its start, how it ended, its time online and by the clock, and its cycles and installs; open one for its cycles, each with its time online, the augmentations its install put in, and any save loaded in it ("left for a save loaded …"), the one it goes on in marked "going on". After each brain start it first reads the store a batch at a time (under a minute for a year's), saying how far it's got, then keeps up as snapshots arrive ([packages/brain](../packages/brain/README.md#the-dashboard)).

## When something's wrong

- **The dashboard says "Brain unreachable", or doesn't load:** the brain isn't running. If its terminal shows `brain runner:` restart lines, it's crashing at start: the lines before them say why. If the terminal was closed, start it again.
- **A `deployFailed` alert:** the brain couldn't deploy to the game. The alert and the brain's output say why. It retries each time the game connects; Options → Remote API → Connect makes it reconnect now.
- **A `versionDrift` alert:** the game isn't the version this release was built for, usually because Steam updated it. The brain holds: it deploys nothing, restarts no Agent, and gives the hack loop no new instructions (only "Stop the hack loop" still gets through); loops already running keep running. Wait for a release built for the new version.
  - The alert says what differs. If the dashboard's Agent table still says "the pinned one" on its "Version" line, the game's API definitions differ under the same version: tell the developer.
- **A `supervisionGaveUp` alert:** the game was relaunched 3 times in an hour, or the supervisor's checks or launch commands kept failing. Check the game and Steam, then click "Resume supervision".
- **An `agentSilent` alert:** no heartbeat for over a minute. If it lasts, the supervisor relaunches the game after 5 minutes. If the game is running and the Agent isn't, `run agent/boot.js` in the terminal starts it.
