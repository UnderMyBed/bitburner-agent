# Setup

How to run the agent against Bitburner on Steam, from a clone of this repository ([#95](https://github.com/UnderMyBed/bitburner-agent/issues/95), [#122](https://github.com/UnderMyBed/bitburner-agent/issues/122); architecture §10.1, §10.2). The brain runs from the repo, in a terminal, and is started again if it crashes. It launches the game, deploys the in-game Agent, and keeps both going while it runs.

**Nothing is installed.** There's no service, no scheduled task and no standalone binary (owner decision 30). Everything the brain writes goes in the repo's gitignored `.data/`: its config (with the control channel's token), the store, the in-game build and the save backups, unless you give it another data directory (below). npm's own download cache is the one exception. To stop it, stop the brain. To remove it, delete the clone, after copying out any save backups in `.data/saves/` you want to keep.

**You run these steps yourself.** They act on your game. Claude builds the agent but never drives your game or your system.

## Before you start

- Windows, with Steam and Bitburner installed (Steam app 1812820).
- [Node.js 26](https://nodejs.org/) and git. The brain runs on 26 or later; the simulator's scripts need 26 itself (below). The pin moved from 24 to 26 after 1.0.1 ([#301](https://github.com/UnderMyBed/bitburner-agent/issues/301)). `v1.0.1` and earlier pin 24 in `.node-version` only, with no `mise.toml`, so mise gives them your global Node there; set `MISE_NODE_VERSION=24` to run one on 24.
- **Which Node runs in the clone.** The repo pins Node 26 in `.node-version`, which CI follows. If you use [mise](https://mise.jdx.dev/), the repo's `mise.toml` selects Node 26 inside the clone, with no global change: mise doesn't read `.node-version` by default, so without it your global mise Node would run here. Check with `node --version` in the clone. On the reference machine mise used it without a `mise trust`; if mise asks for one, run `mise trust` in the clone. If mise doesn't have a Node 26 yet, `mise install node@26` adds one to mise's own folder. A `MISE_NODE_VERSION` you set still overrides the repo's choice. The simulator's scripts (`npm run sim`, the baseline and the bench) refuse any other major, exiting 2 with what to do: seeded games differ between Node majors ([#282](https://github.com/UnderMyBed/bitburner-agent/issues/282)). Node 26's V8 should be the one in Steam's Electron, so on 26 they sort as Steam's game does.
- **One brain, one game.** The brain serves one game on the fixed ports 12525–12527: run one brain at a time, and don't point a second game at it.

## 1. Clone and bootstrap

Only tagged releases go to Steam (architecture §6). Clone the repository and check out the newest release tag. `v1.0.0` is the example below (`v0.2.0` was the first with these steps).

For a release's live run on Steam ([releasing](releasing.md) step 2), check out the candidate commit instead. It's recorded on the milestone's review issue. Then follow [this page as it is on `main`](https://github.com/UnderMyBed/bitburner-agent/blob/main/docs/setup.md), not the copy in your checkout: docs fixed after the candidate are only there.

**Already have a clone?** Use it. Stop its brain if it's running, then follow [Upgrading to a new release](#upgrading-to-a-new-release) with the tag or commit you want. That ends with step 2's `npm run brain`, so carry on at step 3. Its `.data/`, if it has one, carries over: the config, the store and the save backups.

```
git clone https://github.com/UnderMyBed/bitburner-agent.git
cd bitburner-agent
git checkout v1.0.0
npm run bootstrap
```

`npm run bootstrap` fetches the game's source (the `vendor/bitburner-src` submodule), installs this repository's packages, then the game's own dependencies. It says each step, stops at the first that fails, and can be run again. The brain needs the submodule: it checks the game's version against it, and stops at start if it's missing.

## 2. Start the brain

```
npm run brain
```

It runs in that terminal until you stop it (Ctrl+C) or close the terminal.
- **If the brain crashes, it's started again** after 5 s, then 10, 30 and 60 s if it keeps crashing; a run of 5 minutes or more starts that over. Each restart is a `brain runner:` line.
- **After a reboot**, run `npm run brain` again: nothing is installed to do it for you.

**What happens next.** The brain:
- builds the in-game code (a few seconds);
- creates `.data/config.json` in the repo, the first time;
- serves the dashboard at **http://127.0.0.1:12527/**;
- **launches Bitburner through Steam about 30 s later**.

The brain's output is its log: deploys, connections, save backups, errors. If it stops at start, the last lines say why. A `config.json` it doesn't accept names the field and what it should be.

**A config from an earlier brain** may lack fields added since: `saveBackupIntervalMinutes`, `saveBackupsKept`, `steamAppId`, `gameExecutable`. Add them with their defaults ([the brain's README](../packages/brain/README.md#the-data-directory)), or move `.data/` aside and start fresh. A config from v1.0.0 needs nothing added: `telemetryKeptWholeDays` is optional, and absent means no thinning at the start (below).

## 3. Pause supervision while you set up

**Wait for the game to open, then open http://127.0.0.1:12527/ and click "Pause supervision".** If it has been more than a minute and the game hasn't opened, start it from Steam yourself. While supervision runs, the brain kills and relaunches a game that has no Agent reporting for about 5 minutes. Until you've finished step 4, no Agent reports.

An `agentSilent` alert is expected until step 4.4.

## 4. Set the game up

1. **A brand-new save:** click "Exit Tutorial" first, in the tutorial's panel. While the tutorial runs, the game's terminal runs only the tutorial's commands, so step 4.4's `run agent/boot.js` would be refused, and the agent can't end it for you ([architecture §5.7](architecture.md#57-bootstrap-and-restart-c5)).
2. **Options → Remote API:**
   - Hostname `127.0.0.1` (not the default `localhost`: the brain listens on 127.0.0.1 only);
   - Port `12525`;
   - Reconnection delay `5` (above 0, so the game reconnects when the brain restarts);
   - "Use wss" off;
   - then click **Connect**. Changing the settings alone doesn't connect.

   The dashboard's **Recent events** should show `deployed` (or `deploymentCurrent`) and a `saveBackup` within a few seconds.

   **If it doesn't connect** and the dashboard's events show `connectionRejected`, the game's page sent an origin the brain doesn't allow. The brain allows `file://`, Steam's page, by default.
   - Copy the origin from the event, without the ` (Remote File API)` the brain adds after it, into `allowedOrigins` in `.data/config.json`. Never add `(none)`: that's a connection with no origin at all, not a page.
   - Then restart the brain: Ctrl+C, and `npm run brain` again.
3. **Options → System:** set "Autoexec Script + Args" to `agent/boot.js`. Autoexec runs on every load of a saved game, so after this the Agent starts by itself.
4. **First start of the Agent:** in the game's terminal, type `run agent/boot.js` once. Autoexec can't do this first start: it ran when the game loaded, before the brain had deployed.

   The dashboard's **Agent** table shows "Connected: yes" with the deployment, and the tiers start arriving.
5. **Save the game** (Options → Save Game), or wait for an autosave. The game keeps its settings in the save, so settings changed after the last save are lost if the game is relaunched.

## 5. Resume supervision

Click **"Resume supervision"**. From now on, while the brain runs, it relaunches the game if it closes, or if the Agent goes silent for 5 minutes. It does so at most 3 times an hour; after that it stops and shows an alert.

The skeleton now runs as long as the brain does. After a reboot, run `npm run brain` again: the brain launches the game, and autoexec starts the Agent.

## Day to day

- **The hack loop** (since v0.3.0) is on by default (owner decision 34). Once the Agent connects, it roots the servers it can and runs a loop on the game's servers against the target the brain picks; the dashboard's "Hack loop" line names it. When a better target comes within reach, the largest servers prepare it while the rest keep earning, and the line names that too ("preparing zer0 on 7 servers"); all move to it once it's ready. Each server hacks with only so many threads that, together, they never take more of a target's money than it grows back quickly, so money keeps rising: the line says how many ("hacking with at most 48 threads", #187). It never runs on home, your Hacknet servers or your own cloud servers, only the game's servers and the brain's own cloud servers (#194), and it never touches your own scripts ([the hack loop](../packages/ingame/README.md#the-hack-loop)).
  - **With the batcher on** (its default since #206), the batcher hacks from these servers instead and the hack loop only roots; switch the batcher off and the loops come back.
  - **It fills the free RAM** on the servers it runs on, so a script you start there later may not fit. A loop you kill comes back within about 30 s. To use those servers yourself, stop the loop first.
  - **Money flat for 10 minutes** with the loop on is the dashboard's `incomeStalled` alert, with how long, the money and the target, and a line in the brain's window as it starts and ends. A purchase lowers money, which doesn't count as a rise. It shouldn't happen: if it does, `npm run report` names the stall, and it's worth an issue.
  - **To stop it,** click **"Stop the hack loop"** on the dashboard: every loop stops within a few seconds, and it stays off, across brain restarts, until you start it again.
- **The batcher** (since v1.0.0) is on by default (#206, [owner decision 49](decisions/owner-decisions.md)), with the hack loop on: the brain hands the hack loop's servers to the batcher instead, and the hack loop still roots. It runs from home once home has 16 GB, or from your largest rooted server, and hacks in batches (hack, weaken, grow, weaken, each landing in order). **Since #340 its batches run on home too,** on home's RAM beyond what it keeps for the Agent and its workers: 32 GB, plus with Singularity (BN4 or SF4) the most its largest Singularity worker takes at your SF4 level, as sharing keeps (so from home of about 36 GB, about 70 in BN4). **While you work for a faction,** home batches only if the batches earn more with it, relatively, than sharing on home would raise your reputation (a placeholder until the planner splits home's RAM, owner decision 67): late in a BitNode, with cloud servers, home shares; after an install, with home most of your RAM, it batches. The brain's window says "home sharing rather than batching" while it shares. When levelling mode starts, the batcher's operations still running are stopped too, so the level loop has their RAM at once. After an install, home is most of your RAM: in the simulator's first hour after one, with home at 4 TB and no cloud servers, the batches earned 8.7 to 12.5 times what they did without home. Home is filled after your other servers, and what it keeps stays free beside everything running there. **The brain picks its target:** the one worth most over the next 15 minutes, counting the time to prepare it, so it starts on n00dles. A richer server is prepared as the next one, on the RAM the batches leave (a fifth at least), and it moves there once that server is ready (#236), so a move costs a couple of minutes without a hack at most. Its share and spacing follow your hacking level as it rises. In the simulator it earns 1.41 to 1.82 times what the hack loop does on A1's measure (about 30% of the best a batcher could earn on your servers, against the hack loop's 16 to 20%), and far more money. The dashboard's "Batcher" lines say where it runs and against what, and its health: batches, hacks, and any desync (a landing out of order, or the target's money or security outside what a batch in step leaves), which it recovers from by itself; a desync, a late or lost operation, or a problem shows red, the dashboard's `batcherOutOfStep` alert says so, and the run report fails the run, unless a page stall, a delivery lag the page was behind (#309), or (for a batcher before #251) a clock step explains it and the batcher recovered by itself (a warning, #241). The brain's window logs each change of target, of the next target, and of mode (the hack loop takes over when no server holds the batcher). If it can't start (no room on its server, say), the Agent tries again within seconds; still down after 3 snapshots, the dashboard's `batcherNotRunning` alert says why, and the run report fails, since nothing hacks the servers the hack loop left to it. **"Stop the batcher"** stops it within a few seconds and the hack loop takes its servers back; it stays off across brain restarts until you start it again ([the batcher](../packages/brain/README.md#the-batcher)).
- **Sharing spare RAM** (since v1.0.0, #224, on by default, [owner decision 52](decisions/owner-decisions.md)): while you work for a faction (work set on the dashboard, or the brain's; work you start by hand in the game isn't seen), the batcher shares the RAM its batches leave, and home's above 32 GB, with `ns.share()`, which raises the reputation faction work earns: about 1.6 times for hacking work on the 26 PB of the first overnight run (field and security work gain less: only their hacking and intelligence part is raised). Batches always come first: it keeps their peak RAM, a quarter more, and the next target's free, never takes the batcher's servers past 80% in use (home beside them isn't counted), and starts a round every 5 s at most, each lasting 10 s, on half of what it may share, so as one round ends the other still shares (#242). Home shares whenever you work for a faction, whatever the batches are doing, while it isn't one of the batcher's servers; once it is (#340: home past about 36 GB, about 70 in BN4), its RAM goes to the batches first and it shares as they do, unless the share on home beats what home adds to the batches (above). Early on, when the batches need all the RAM, it shares nothing. With the batcher off, nothing shares. The dashboard's "Batcher" lines show its threads, RAM and bonus, and the "Sharing spare RAM" section why it isn't asked while it's on; the run report says how long it shared and at what bonus, and fails if a batch came up short of RAM, or was planned smaller for the share's threads, while it shared on the batcher's servers (a short while only home shares is the batcher's own, `batches short of RAM` below, #230), or if it was asked, had room, and shared nothing for 10 minutes, or, while asked, left over half of what home may share (its RAM beyond what it keeps) free for 5 minutes (#242). It also shows the bonus on average while asked against the bonus possible under the share's rules, and the time at no bonus. With Singularity (BN4 or SF4), home keeps 32 GB plus the most its largest Singularity worker takes at your SF4 level, not all of home. **"Stop sharing spare RAM"** stops new rounds at once; the last ends within 10 s (work you stop by hand, within about 40 s) ([sharing spare RAM](../packages/brain/README.md#sharing-spare-ram)).
- **Buying the hacking programs** (since v0.3.0) is on by default too. When you can afford the next one, the Agent buys the TOR router at your city's tech vendor, then BruteSSH.exe, FTPCrack.exe, relaySMTP.exe, HTTPWorm.exe and SQLInject.exe through the terminal, so the hack loop can root more servers ([the hacking programs](../packages/ingame/README.md#the-hacking-programs)).
  - **It uses the game's page, as you would:** a few times a session you'll see the page switch to the City and back, or a `buy` typed into the terminal. However it goes, it ends on the Terminal, or, if you were focused on work, focused on it again.
  - **Keep the sidebar's Hacking, Character and World sections open:** they hold the Terminal, Factions, City and Job. With one collapsed, what goes through it (buying, joining a faction, buying an augmentation, starting work at a faction or a company) waits until it's open again.
  - **The faction state** (since v1.0.0, #197): to read each faction's reputation and favour, the invitations and the augmentations bought but not installed, the Agent opens the Factions page (and the Augmentations page while anything is queued) when it starts, and after that only when something there may have changed (a faction joined, an invitation, a purchase, an install) or every 10 minutes while you've joined a faction or have an invitation. In between it reads the reputation of the faction you work for from the page as it is, and nothing moves. After a read it puts the page back as it found it: your work focused again, or the page you were on (a location's page goes back to the City map, and a faction's augmentations to the Terminal). It never reads while the casino is open: leaving mid-hand would forfeit your bet. The reputation of factions you aren't working for may be up to 10 minutes old. With Singularity (SF4) and room on home, none of this touches the page.
  - **The game's own dialogs are handled for you** (owner decision 35): the Agent closes the game's alerts ("Offline for…" after a load, purchase and travel notices), and answers a faction invitation with "Decide later", so it waits on the Factions page. What each said is on the dashboard's recent events (`gameDialog`). Any other dialog (a script's `ns.prompt` or `ns.alert`, or one you opened) is yours: nothing is done on the page while it's open, and the dashboard's `dialogBlocking` alert quotes it. Nothing is typed into the terminal while you've a line typed there either.
  - **Chongqing and New Tokyo have no tech vendor:** in either, the TOR router waits until you travel, and the dashboard says so.
  - **Nothing is bought while the brain holds** (after a Steam update, a failed deploy, or a game version it wasn't built for).
  - **To stop it,** click **"Stop buying programs"** on the dashboard; **"Start buying programs"** turns it back on.
- **Upgrading home's RAM** (since v0.3.0) is on by default too. When you can afford it, the Agent doubles home's RAM at your city's tech vendor, the same way: the page switches to the City and back to the Terminal once per upgrade ([home RAM](../packages/ingame/README.md#home-ram)).
  - **One purchase at a time, the cheaper first:** with buying programs on too, the upgrades and the programs take turns by price (16 GB comes after BruteSSH.exe and before FTPCrack.exe), and the dashboard says which one waits for which. So while an upgrade can't be made (World collapsed), the next program waits for it too.
  - **BN1, BN2, BN4, BN5, BN6 and BN7 only, for now** (#321, #323, #334, #367): their price is BN1's; other BitNodes change it, so there it waits, and the dashboard says so.
  - The same as for the programs: keep the World section open, close your own dialogs (and your scripts'), travel from Chongqing or New Tokyo, and nothing while the brain holds.
  - **To stop it,** click **"Stop upgrading home RAM"** on the dashboard; **"Start upgrading home RAM"** turns it back on.
- **Buying cloud servers** (since v1.0.0, #194) is on by default too. The brain buys cloud servers (`pserv-0`, `pserv-1`, …) through the NS API, with nothing on the page, and the hack loop runs on them. Your own cloud servers, under any other name, are left to you: the loop never runs on them and the brain never upgrades them, but they count toward the game's limit of 25 ([cloud servers](../packages/brain/README.md#cloud-servers)).
  - **When:** once the hack loop has earned for 10 minutes, it measures what a GB of its servers earns a second, and buys the largest server money allows if it pays for itself within 15 minutes at that rate. That comes once the loop has moved past n00dles to a richer target: in the simulator, 80 to 100 minutes into a fresh start. At the game's limit of 25, it upgrades its smallest instead. BN1, BN2, BN4, BN5, BN6 and BN7 only, for now (#321, #323, #334, #367: BN2's, BN4's, BN5's, BN6's and BN7's bigger servers cost more a GB).
  - **After the programs and home RAM:** one purchase at a time, those first. While the next program or home RAM upgrade waits for money, and the income would bring what's short within a minute, that money is kept for it.
  - **The dashboard's Cloud servers section** says what it's buying, for how much and how soon it pays back, or what it waits for, and lists your cloud servers.
  - **If a purchase goes wrong** (bought under another name), the `cloudServerProblem` alert says so and it buys no more: look at the alert, then turn it off and on again. A restarted brain forgets the hold, but the run report still fails on that purchase.
  - **To stop it,** click **"Stop buying cloud servers"**; **"Start buying cloud servers"** turns it back on.

## Upgrading to a new release

Stop the brain, then:

```
git fetch --tags
git checkout v1.0.0                 # or the candidate commit, for a live run
npm run bootstrap
npm run brain
```

The brain builds the new in-game code at start and deploys it when the game connects. The running Agent hands over to the new one by itself. Release notes say if `config.json` needs new fields.

## After a run: the run report

After a live run (or during one), `npm run report` says what the run did and what went wrong, from the brain's store alone, so nobody has to dig through SQLite by hand (owner decision 45). It reads; it never changes anything, so it's safe while the brain runs.

```
npm run report                                                  # from the newest brain start to now (or its stop)
npm run report -- --since 2026-10-28T21:26:00Z --until 2026-10-28T22:40:00Z
npm run report -- --verbose                                     # every intent, purchase, dialog and choice
```

## The campaign report

`npm run campaign` is the campaign's scoreboard: every BitNode in the store, across every run and brain restart, with how long it took to destroy, its cycles and installs, and which release played it (#290). It's what the releases are judged on ("did v1.0.1 clear BN1.4 faster than v1.0.0?"). Like the run report it only reads, so it's safe while the brain runs.

```
npm run campaign
```

It prints:
- **A row per BitNode** ("BN1.2": the number and level; "BN1.4 #2" for one played again): its start, how it ended, the time to its end by the clock and **online** (the game and the brain both up), the time **left out** of that (the game closed, or the brain or the Agent away for over 3 minutes: the game goes on offline, so this says how much of a clear wasn't watched), the cycles, the installs (and how many **by hand**: from your queue, the game's Install button or a Soft Reset, not the brain's own rule), the augmentations installed, the brain starts, and the releases. "≥" marks what's at least that: a BitNode begun before the store's first record or reached by loading a save, or whose first look showed an install already. Under it, each BitNode's Source-Files as entered, its time online by release, its augmentations by name, and any save loaded in it.
- **How a BitNode ended:**
  - **destroyed**: its Source-File went up a level, or at the Source-File's cap (level 3) the brain sent the destroy just before; with its Source-File overridden in the BitNode's options, the brain's destroy says it, else it's **unknown**;
  - **destroyed, BitNodes unseen**: its Source-File went up more than a level, or another one rose too, so BitNodes were played that the store didn't see (never a clear of its own); **BitNodes unseen** where only another rose;
  - **a save loaded**: the next BitNode's start is before this one's last look, so a save was loaded, older or newer (never counted as a destroy);
  - **a new game**: a Source-File was lost, or there was none (b1t_flum3 needs one);
  - **b1t_flum3**: another BitNode with no Source-File gained (at the cap, it could also be a destroy you did by hand);
  - for the newest BitNode, **destroy sent**, the next BitNode not seen yet, or **not yet**.
- **A row per release and BitNode it played:** its time online there, its cycles and installs, and whether it destroyed it. "A clear of its own" is a BitNode one release played from its start to its destroy, with no install by hand and no save loaded in it ("yes, with a save loaded in it" otherwise): the fair comparison. Another release that played only its first 5 minutes or less, with no install (a brain upgraded just after a destroy), doesn't stop it; its share is printed beside the clear (owner decision 61).
- **Compared:** each BitNode two releases or more cleared on their own, the fastest online first, with each clear's time left out and the Source-Files it was entered with.
- **The time to the destroy** (#360, last): the brain's estimate of the time online to each BitNode's destroy, at its start, each install, Daedalus joined and levelling's first choice, against the outcome: a row each (the moment, the time online then, the estimated remaining and total, the actual, their ratio, and the terms: A the count, BC the invitation and The Red Pill, D w0r1d_d43m0n's level). Before the brain made them (a store from before #360), they're hindcast from the store as it was then and marked so; BN2's (the gang's route, #357) aren't, so its rows are the brain's own. Then each BitNode's median and worst ratio, and the ratios by moment. "≥" marks an estimate that's at least that (a term with nothing to go on: no BitNode destroyed before it, or one at another w0r1d_d43m0n level); "under 10 min left" one whose ratio the minute-by-minute record can't measure to 10%. Both are left out of the medians.

A release is the brain's version (`git describe`, "v1.0.1"), whatever the Agent's build. Upgrading mid-BitNode splits its time between the two releases, so neither has a clear of its own there. Running the brain from an untagged or changed checkout makes every commit its own release ("v1.0.0-4-gabc1234"), so a clear to compare is a tagged release's.

It exits 0 with the report, and 2 when it couldn't run: no store, or no BitNode in it.

**The dashboard's "BitNodes and installs"** (#285) shows the same campaign while the brain runs: each BitNode, the newest first, with its start, how it ended, its time online and by the clock, and its cycles and installs; open one for its cycles, each with its time online, the augmentations its install put in, and any save loaded in it ("left for a save loaded …"), the one it goes on in marked "going on". After each brain start it first reads the store a batch at a time (under a minute for a year's), saying how far it's got, then keeps up as snapshots arrive ([packages/brain](../packages/brain/README.md#the-dashboard)).

## When something's wrong

- **The dashboard says "Brain unreachable", or doesn't load:** the brain isn't running. If its terminal shows `brain runner:` restart lines, it's crashing at start: the lines before them say why. If the terminal was closed, start it again.
- **The brain's terminal says `held in the last 1 min: …`** (or less, as it stops) (#309): something held the brain's event loop over 0.2 s, and every snapshot arriving meanwhile reached it late (the run report's delivery lags). It names the dashboard's statuses built slower than 200 ms, if any, and the loop's longest hold. Nothing to do in the game: the brain carries on. Closing the dashboard's tab stops its statuses; put the line, with its time, on an issue, since a slow status or a long hold is a bug of ours.
- **A `deployFailed` alert:** the brain couldn't deploy to the game. The alert and the brain's output say why. It retries each time the game connects; Options → Remote API → Connect makes it reconnect now.
- **A `versionDrift` alert:** the game isn't the version this release was built for, usually because Steam updated it. The brain holds: it deploys nothing, restarts no Agent, and gives the hack loop no new instructions (only "Stop the hack loop" still gets through); loops already running keep running. Wait for a release built for the new version.
  - The alert says what differs. If the dashboard's Agent table still says "the pinned one" on its "Version" line, the game's API definitions differ under the same version: tell the developer.
- **A `supervisionGaveUp` alert:** the game was relaunched 3 times in an hour, or the supervisor's checks or launch commands kept failing. Check the game and Steam, then click "Resume supervision".
- **An `agentSilent` alert:** no heartbeat for over a minute. If it lasts, the supervisor relaunches the game after 5 minutes. If the game is running and the Agent isn't, `run agent/boot.js` in the terminal starts it.
