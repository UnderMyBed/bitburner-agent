# @bitburner-agent/brain

The long-running brain process (architecture D1): the bridge to the game, the telemetry store, and from M4 phase B the planner. Since M2 ([v0.2.0](https://github.com/UnderMyBed/bitburner-agent/releases/tag/v0.2.0)) it runs the control channel and stores what the in-game Agent reports, and serves the Remote File API, over which it deploys the in-game code ([#91](https://github.com/UnderMyBed/bitburner-agent/issues/91)) and backs up the game's save ([#92](https://github.com/UnderMyBed/bitburner-agent/issues/92)). It also serves the local [dashboard](#the-dashboard) ([#93](https://github.com/UnderMyBed/bitburner-agent/issues/93)), and, for Steam on Windows, [supervises](#supervision) the game itself ([#94](https://github.com/UnderMyBed/bitburner-agent/issues/94)). Since M3 ([v0.3.0](https://github.com/UnderMyBed/bitburner-agent/releases/tag/v0.3.0)) it tells the Agent what to run, in one desired state: [the hack loop](#the-hack-loop) and its target ([#134](https://github.com/UnderMyBed/bitburner-agent/issues/134)), its move to the next target without an income stall, with the `incomeStalled` alert ([#184](https://github.com/UnderMyBed/bitburner-agent/issues/184)), and its hack threads per host, so it doesn't drain the target ([#187](https://github.com/UnderMyBed/bitburner-agent/issues/187)); the purchases of [the hacking programs](#the-hacking-programs) and [home RAM](#home-ram) ([#136](https://github.com/UnderMyBed/bitburner-agent/issues/136), [#138](https://github.com/UnderMyBed/bitburner-agent/issues/138)); the owner's queue of [intents](#intents) ([#141](https://github.com/UnderMyBed/bitburner-agent/issues/141)), the irreversible ones behind a gate with a save backup ([#147](https://github.com/UnderMyBed/bitburner-agent/issues/147)), installs and destroys counted done across the reset ([#164](https://github.com/UnderMyBed/bitburner-agent/issues/164), [#175](https://github.com/UnderMyBed/bitburner-agent/issues/175)); [work](#work) ([#151](https://github.com/UnderMyBed/bitburner-agent/issues/151), [#153](https://github.com/UnderMyBed/bitburner-agent/issues/153), [#156](https://github.com/UnderMyBed/bitburner-agent/issues/156), [#158](https://github.com/UnderMyBed/bitburner-agent/issues/158)); and the state [safe mode](#safe-mode) keeps with the brain down ([#160](https://github.com/UnderMyBed/bitburner-agent/issues/160)). The dashboard has their switches and forms. [The run report](#the-run-report), `npm run report` ([#185](https://github.com/UnderMyBed/bitburner-agent/issues/185)), reads a live run back from the store. Since M4 phase A ([v1.0.0](https://github.com/UnderMyBed/bitburner-agent/releases/tag/v1.0.0), a playable BN1, [#191](https://github.com/UnderMyBed/bitburner-agent/issues/191)), it plays BN1 on its own, its choices computed from the game's formulas ([owner decision 46](../../docs/decisions/owner-decisions.md)): [the hacking ceiling](#the-hacking-ceiling), and what hacking earns against it ([#196](https://github.com/UnderMyBed/bitburner-agent/issues/196)); [cloud servers](#cloud-servers) bought and upgraded by their payback ([#194](https://github.com/UnderMyBed/bitburner-agent/issues/194)); [the batcher](#the-batcher), proven on the engine, run by the Agent and given its targets by the brain ([#204](https://github.com/UnderMyBed/bitburner-agent/issues/204), [#205](https://github.com/UnderMyBed/bitburner-agent/issues/205), [#206](https://github.com/UnderMyBed/bitburner-agent/issues/206)); ## Running it

```
npm run brain
```

From the repo, in a terminal, until stopped (Ctrl+C). Nothing is installed (owner decision 30). `npm run brain` runs `src/start.ts`, which runs the brain (`src/main.ts`) as a child process and starts it again after a crash: after 5 s, then 10, 30 and 60 s in a crash loop, back to 5 s after a run of 5 minutes (`src/restart-on-crash.ts`). Ctrl+C reaches both, the brain shuts down cleanly, and nothing is restarted. After a reboot, run it again. [docs/setup.md](../../docs/setup.md) has the owner's steps, from a clone (`npm run bootstrap`) to a running skeleton. One brain per game.

- **On Windows, an E0 brain (the default) runs the game itself.** Within 30 s it launches Bitburner through Steam. If no Agent reports for about 5 minutes, it kills and relaunches the game ([Supervision](#supervision)). Pause supervision on the dashboard while you set the game up.
- **The data directory is the repo's `.data/`** (gitignored), so everything stays in the repo ([#122](https://github.com/UnderMyBed/bitburner-agent/issues/122)). `--data-dir <dir>` or `BITBURNER_AGENT_DATA_DIR` picks another; a relative path is taken from the directory the command was run in. Tests always pass their own (with an E2 config): a brain started in `.data/` creates an E0 config, which on Windows launches Steam's game.
- **Logs** go to stdout, one line per event, each cut at 500 characters; fatal errors go to stderr, and the brain exits non-zero. The startup lines name the release, the deployment it deploys, the control channel's and the Remote File API's ports, where the save backups and the data backups go, the dashboard's address, whether it supervises the game, and whether the hack loop, the program buying, the home RAM upgrades, the cloud servers, the brain's faction work, and buying and installing augmentations are on. Each switch flipped on the dashboard is logged too ("the brain's faction work turned off from the dashboard", #203), and so is an income stall as it starts and as it ends (`incomeStalled`, #184), and the faction state unread, when its problem changes, and read again ("the faction state couldn't be read (ui): …", "the faction state is read again (ui)", #197), and the backdoors, joins and faction work ([backdoors](#backdoors-for-the-hacker-factions), [factions](#factions-and-their-work)).
- **At start it thins the store's old data only if `config.json` opts in** ([thinning](#thinning), #283): with `telemetryKeptWholeDays` set, fast and medium snapshots older than that many days before the newest snapshot are cut to one whole a minute, before its `brainStarted`, and logged ("store thinned before …"), once a [data backup](#the-data-backup) holds them (#284: one is taken first if none does). Without it (the default) it logs "store thinning at start: off …". A thinning that fails is logged and is the dashboard's `storeThinningFailed` alert, and the brain starts all the same.
- **It backs its data directory up** ([the data backup](#the-data-backup), #284): the store, `config.json` and the newest save backup of each environment, into `<data dir>/backups/<time>/`, at its start when the newest is a day old or there's none, then each day; the newest 2 kept. The store's copy is made in a worker thread, off the event loop. Each is logged ("data backup backups/… (at the brain's start): the store 412.3 MB, 1 save backup, in 1.7 s"); one that fails is logged, recorded and the dashboard's `dataBackupFailed` alert, and play goes on.
- **It holds a lock file while it runs,** `brain.lock` in its data directory, naming its process and, under `npm run brain`, the runner's (which lives on through a crash and the restart after it). It's claimed before the store is opened, written whole (a file of its own, renamed into place), and removed only on a clean stop: after a crash it stays, and the runner's process keeps it counting until the restart claims it again (#297's re-review). It's never taken from another brain whose process is alive (that one keeps it, and the log says so), and one the brain can't write is logged, never fatal. `npm run thin` refuses while either process is alive (#283's review).
- **At start it builds the in-game code** from its own checkout (`packages/ingame`, with esbuild from `npm ci`) into `<data dir>/ingame-build/`, rebuilt from scratch every start, and checks each file against the build's manifest. So it always deploys the code it was started from, with no separate build step. It also reads the pinned game's definition file, for the version check: the checkout needs the `vendor/bitburner-src` submodule (`npm run bootstrap` fetches it), or the brain stops at start, saying which file is missing.
- **Deploying:** whenever the game connects to the Remote File API (on load, and after a drop, by its own reconnection setting), the brain checks the game's version and deploys if `agent/current.txt` names another deployment ([the steps](../../docs/bridge/protocol.md#deploying)). The very first start of the Agent on a save is by hand: `run agent/boot.js` in the game's terminal; autoexec does it on every load after that (#95).

## The data directory

| File | What |
|---|---|
| `config.json` | Created with defaults on first run, then read |
| `telemetry.sqlite` | The store (below), with its WAL files |
| `ingame-build/` | The in-game code built at start, which the brain deploys |
| `saves/<environment>/` | The game's save backups ([below](#save-backups)) |
| `brain.lock` | The brain's process and its runner's (#283's review): left after a crash, removed on a clean stop |
| `telemetry.pre-thinning-<time>.sqlite` | A copy of the store `npm run thin` made before thinning it ([below](#thinning)); delete it when you no longer want the data |
| `backups/<time>/` | The data backups ([below](#the-data-backup), #284): each a copy of the store, `config.json` and the newest save backup of each environment, the newest 2 kept; elsewhere if `dataBackupDirectory` says |

`config.json`:

| Field | Default | What |
|---|---|---|
| `environment` | `E0` | Which environment this brain serves: `E0` Steam, `E2` a source build under test ([architecture §9.4](../../docs/architecture.md#94-environments)). A simulator's brain (`E1`) runs from code, with no config |
| `controlPort` | 12526 | The control channel ([docs/bridge/protocol.md](../../docs/bridge/protocol.md)) |
| `remoteFileApiPort` | 12525 | The Remote File API server: the game's RFA settings must name it (#91, #95) |
| `dashboardPort` | 12527 | The dashboard (#93) |
| `allowedOrigins` | `["file://"]` | `Origin` headers allowed to connect; `file://` is Steam's page |
| `token` | 32 random bytes, hex | The control channel's shared secret, generated once |
| `saveBackupIntervalMinutes` | 30 | How often the game's save is backed up, besides once on each RFA connection |
| `saveBackupsKept` | 96 | How many save backups to keep per environment, the newest: two days at 30 minutes |
| `steamAppId` | 1812820 | Bitburner's Steam app ID, which the [supervisor](#supervision) launches (E0 on Windows only) |
| `gameExecutable` | `bitburner.exe` | The game's executable, as tasklist shows it: a file name, no folder |
| `telemetryKeptWholeDays` | absent (not written) | Thinning at each start, opted into: the days before the newest snapshot the store keeps whole; older fast and medium snapshots are thinned, which can't be undone ([below](#thinning)). Absent or null: no thinning at the start (`npm run thin` by hand) |
| `dataBackupsKept` | absent (not written): 2 | How many [data backups](#the-data-backup) to keep, the newest; 0 for none (and then no thinning at the start). The owner's call, proposed (owner decision 62) |
| `dataBackupIntervalHours` | absent (not written): 24 | Hours from the newest data backup to the next: at least 1, at most 596 (the longest a timer can wait). The owner's call, proposed (owner decision 62) |
| `dataBackupDirectory` | absent (not written): `backups` in the data directory | Where the data backups go: a folder, relative to the data directory unless absolute. Nothing goes outside the data directory unless you set it (another disk keeps a copy if this one fails) |

A config that isn't valid stops the brain, naming the file and the problem:
- invalid JSON, or not an object;
- another environment;
- ports out of range, or two the same;
- no allowed origins;
- a token that isn't 64 hex digits;
- a backup interval that isn't a number of minutes above 0 and at most 35791 (the longest a timer can wait, about 24.8 days), or a count kept that isn't a whole number of at least 1;
- a Steam app ID that isn't a whole number of at least 1, or a game executable that isn't a bare `.exe` file name;
- days kept whole, when given, that aren't a whole number of at least 1;
- data backups kept, when given, that aren't a whole number of at least 0; an interval that isn't a number of hours from 1 to 596; or a backup folder that's empty or isn't text.

A config from before the backup and supervision fields existed is refused too, naming one missing field and its default at a time. Add them (`"saveBackupIntervalMinutes": 30, "saveBackupsKept": 96, "steamAppId": 1812820, "gameExecutable": "bitburner.exe"`), or start from a fresh data directory.

A port of 0 picks any free port, which is for tests only: the game's RFA settings can't name it, and a control port of 0 changes at every start, so every start would be a new deployment.

## The telemetry store

SQLite through Node's built-in `node:sqlite`, in WAL mode so a reader (the gap report's and the run report's commands) never blocks the brain's writes (architecture §7, §11).

| Table | Rows |
|---|---|
| `snapshots` | Every snapshot the control channel passes on: `environment`, `release`, `agent_session_id`, `tier`, `sequence_number`, `game_time_ms`, `received_at_ms`, `missed_before` (numbers skipped before it; after a brain restart, counted from the highest stored for its session and tier, #119), `data` (JSON) |
| `events` | Everything else the brain's parts report: the brain's own `brainStarted` (at each start), its thinning's `storeThinned` and `storeThinningFailed` (#283, [below](#thinning)), and its data backups' `dataBackup` and `dataBackupFailed` (#284, [below](#the-data-backup)); the channel's `agentConnected`, `agentDisconnected`, `connectionRejected`, `versionDrift`; the deployer's `deployed`, `deploymentCurrent`, `deployFailed`, `versionDrift`; the save backups' `saveBackup`, `saveBackupRotationFailed`; and the supervisor's `relaunch`, `supervisionGaveUp`, `supervisionFailed`. The game's dialogs the Agent handled, as `gameDialog` (#143), with their kind and text. A brain message the Agent refused, as `messageRefused` (#194's review), with its reason and count, stored once. A promotion the Agent took, as `workPromotion` (#155), with the company, the titles before and after, and the game's time, stored once (and logged). A slow snapshot's faction state unread, as `factionStateUnread` (#197), with the backend and the problem, each time the problem changes, and `factionStateRead`, with the backend, once it's read again (both logged). The brain's faction work (#203): each choice as `factionWorkChosen` (the faction, work type, target, reputation, requirement, rate and ETA) and its end as `factionWorkStopped` (`{ reason }`). Augmentations (#210): where the count rule stands each time it changes, as `augmentationProgress` (#222: the counts, the bars, the time online this cycle, when each bar falls next, the countdown and a hold); each install chosen, as `augmentationInstallChosen` (the set and its money, what's queued, the time online this cycle, the counts and bars, and why); each purchase, as `augmentationBought` (the augmentation, faction, level, price and the queue's length); a purchase never shown queued, as `augmentationNotQueued`; a donation shown in its faction's reputation, as `augmentationDonated` (#225: the faction, the amount, the reputation before and after), and one never shown, as `augmentationDonationFailed`; a cycle called off, as `augmentationCycleCalledOff` (`{ reason }`); an install going out, as `augmentationInstallSent` (the brain's or the owner's, and what's queued); and an install reported done with no reset in the next slow snapshot, as `augmentationInstallNotReset` (what's queued, #213 re-review). The World Daemon (#215): a step stalled, as `worldDaemonStalled` (the step, since when, and what's missing), and a destroy going out, as `bitNodeDestroySent` (the brain's or the owner's, and the BitNode); an install while short of Daedalus's count that added none to it with nothing that counts passed over, as `daedalusCountNeuroFluxOnly` (the count, A6's commit's facts and the line, #238). A restart after a reset through the page that couldn't type `run /agent/boot.js`, as `restartFellBack` (#212), with the outcome (the fallback's reload, or given up), the reason and the page's time, from the next Agent's first fast snapshot (and logged). Columns: `environment`, `release`, `at_ms`, `kind`, `detail` (JSON) |
| `settings` | Switches kept across restarts: `supervision.paused` (the dashboard's switch), `supervision.gaveUpAtMs` (the supervisor's give-up, #94), `hackLoop.enabled` (the hack loop's switch, on when unset, #134), `work.desired` (the work the owner set on the dashboard, #151, #153, #156, #158), `programs.enabled` (buying the hacking programs, likewise, #136), `homeRam.enabled` (upgrading home's RAM, likewise, #138), `cloudServers.enabled` (buying cloud servers, likewise, #194), `factionWork.enabled` (the brain's faction work, likewise, #203), `augmentations.enabled` (buying and installing augmentations, likewise, #210), `augmentations.online` (the count rule's clock, the game's time seen online this cycle, keyed by its `lastAugReset`, #222), `augmentations.countHold` (the window of a hold for Daedalus's count: its cycle's `lastAugReset` and the time online at its start, #243), `augmentations.cycle` (the install chosen: the `lastAugReset` it was chosen in, and whether it's asked for, #210), `worldDaemon.enabled` (destroying the BitNode, on when unset, #215), `share.enabled` (sharing spare RAM, on when unset, #224), `intents.manual` (the owner's manual intents queue, as `[{ action, args }]`, #141), and `intents.resetSent` (the note of a sent install or destroy, `{ id, field, resetAt }`, #175) |

- **Every snapshot and event is tagged** with its environment and its release, so releases and environments can be compared directly (§7). The release is:
  - the brain's `git describe` ("unknown" without git, which the startup log shows);
  - plus the deployment of the Agent connected when the row arrived, or `none` while no Agent is. A deployer or save-backup event's is the deployment the brain deploys.

  For example, `v0.2.0+3f2a1b…`.
- **Writes wait up to 5 s** for a reader's lock, so a reader never fails a write.
- **Timestamps** (`received_at_ms`, `at_ms`) come from the brain's clock: the system clock live, virtual time under the simulator.
- **Thinned only when asked** ([below](#thinning)): a day of snapshots is about 50,000 rows, and a 12-hour run's about 200 MB.

### Thinning

The campaign's months of data, kept to what its readers need of old runs ([#283](https://github.com/UnderMyBed/bitburner-agent/issues/283), `src/store-thinning.ts`; [the spec](https://github.com/UnderMyBed/bitburner-agent/issues/283#issuecomment-6711790410), and its review's changes). **Thinning can't be undone:** what a stub drops is gone, and keeping more days later doesn't bring it back. Only a backup has it (`npm run thin` makes one first; at the start, a [data backup](#the-data-backup) holds it, #284).

- **Off unless the owner opts in** (owner decision 60, proposed in #283): by default nothing is ever thinned, and the store keeps everything. `npm run thin` thins by hand. Set `"telemetryKeptWholeDays"` in `config.json` to thin at each brain start too, once a [data backup](#the-data-backup) holds what it cuts (#284). To keep everything, do nothing.
- **The rule:** fast and medium snapshots received more than `telemetryKeptWholeDays` (`npm run thin`: 14 unless said) before the **newest snapshot** are thinned; nothing else. The cutoff is on a minute. A brain started after a long pause thins nothing it hasn't already, and the dashboard's newest readings are never thinned. With the newest snapshot after now, a clock is wrong: nothing is thinned, and the line says why, so a clock set wrong can't thin real data. Before the cutoff:
  - every event, setting, static and slow snapshot, and the first fast and the first medium snapshot stored in each minute (the brain's clock), stay whole;
  - each other fast and medium snapshot keeps its row, its times (the brain's and the game's), session and sequence number, and its data becomes a stub (`TelemetryStore.thinSnapshots`): `{"thinned":true,"degradedTiers":[…],"pageHeapUsedBytes":…,"resetIntents":[…]}` for a fast one (`resetIntents`: the ids of the install and destroy intents it held, which a gap's reload reads, #240), `{"thinned":true}` for a medium one (`isThinnedReading`). That's 29 in 30 fast and 5 in 6 medium snapshots, most of the store's bytes; a stub's row is about 250 bytes.
- **When:** from `npm run thin` (below), and, opted in, at the brain's start, before its `brainStarted` (never in a run's hot path).
  - **At the start, only once a data backup holds what it cuts** (#284, `backupBeforeThinning`): the newest backup counts if it's within `dataBackupIntervalHours` and was taken at or after the thinning's cutoff (everything it cuts was stored before it, and none of it thinned yet). Otherwise one is taken first, "(before the start's thinning)". With data backups off (`dataBackupsKept` 0), or the backup failing, nothing is thinned: logged as a failed thinning ("no data backup holds what it would cut (#284): …"), recorded and the `storeThinningFailed` alert. A thinning with nothing to cut asks for no backup. The copy that holds the cut data whole is rotated out with the rest, and it can be up to an interval old when the thinning trusts it, so a start's thinning can be undone from it for between `dataBackupsKept` less one and `dataBackupsKept` intervals: 1 to 2 days by default, and less than a day with 1 kept. `npm run thin`'s own copy is kept until you delete it. Each thinning starts where the last stopped (the newest `storeThinned` event's cutoff), so it reads only what has aged past it since; a first one over months of data reads them all once. It's one write transaction, all or nothing, and the write-ahead log is emptied after one that cut something.
- **What it says:** a line, "store thinned before … (the last 14 days before the newest snapshot kept whole; before, one fast and one medium snapshot a minute): 12345 fast and 2345 medium snapshots cut to their times, their data 180.2 MB → 3.4 MB, in 4.1 s", or "store thinning: nothing to thin before …" (a write-ahead log it couldn't empty after the commit is added to the line, "its write-ahead log not emptied: …": the thinning stands); and, if it cut anything, a `storeThinned` event (the cutoff, where it started, the days kept, the counts by tier, the bytes before and after, the time it took). A thinning at the start that fails is logged ("store thinning FAILED, the store left as it was: …"), recorded (`storeThinningFailed`) and the dashboard's `storeThinningFailed` alert, and the brain starts all the same: losing the store never breaks play. The run report's section 1 lists both events: in its window, and from just before it, since the start's come just before its `brainStarted` ("(before the window)").
- **Never touched:** the save backups (files beside the store), the settings, the events, another environment's snapshots.
- **Its readers:**
  - the run report's time checks (the heartbeat's gaps, clock steps and page stalls, the page heap, the run's end, a gap's reload) read every row, stubs included, so they're exact over a thinned window; its content checks read the whole snapshots, one a minute there ([the run report](#the-run-report)). A thinning's events are never the run's last record;
  - `npm run gaps` reads the times and the page heaps, which the stubs keep: exact;
  - the dashboard and the brain read only recent data and the settings;
  - the fast model's calibration (the medium and slow snapshots at 5, 10, 15 … min after each install, the events, the fast snapshots' `batcher.sharing`): a reading at a mark is within 60 s of the unthinned one (10 s before), `batcher.sharing` is read a minute at a time, and the slow snapshots and the events are exact. A read-only extract skips stubs with `substr(data, 1, 11) <> '{"thinned":'`; a test runs that extract over a thinned store.
- **The file:** SQLite reuses the pages thinning frees, so the file stops growing past its high-water mark, but doesn't shrink. The brain never compacts it; `npm run thin -- --vacuum` does, on demand.

```
npm run thin -- [--data-dir <dir>] [--environment E0] [--kept-whole-days <days>] [--dry-run] [--no-backup] [--vacuum]
```

- **Refused while the brain runs,** every time: its lock file names a live process (the brain, or its runner between a crash and the restart), or something answers on `config.json`'s dashboard port. A thinning holds the store's write lock for its whole run, longer than the brain's writes wait (5 s). A lock left by a killed brain with no runner names dead processes, so it doesn't count; one naming a process id the system has since given to another program is taken as running, and the message names the file to delete. `--vacuum` checks again just before its swap, and if the brain has started meanwhile it removes its copy and leaves the store as it is.
- **The days:** `--kept-whole-days`, else `config.json`'s `telemetryKeptWholeDays`, else 14; the environment `config.json`'s unless `--environment`. It reads `config.json` without creating one.
- **`--dry-run`** prints what it would cut, by tier, and the bytes before and after, and changes nothing.
- **A backup first:** before a thinning that cuts anything, it writes a compacted copy of the store, `telemetry.pre-thinning-<time>.sqlite` in the data directory (SQLite's `VACUUM INTO`), and prints its path and size; `--no-backup` skips it. A copy that fails part-way (the disk full, say) is removed, never left looking good. It takes seconds a GB.
- **`--vacuum`** then compacts the store: a compacted copy written beside it (`telemetry.sqlite.compacted`; a stale one from a stopped run is removed first, and a partial one on failure), then swapped in, so nothing goes to the system's temp folder. It takes seconds to minutes at GBs, and prints the size before and after.
- **Free space:** the backup is about the store's size less its free pages, and kept; `--vacuum`'s copy is the thinned store's size, while it runs. So the peak is about twice the store's size (the store and its backup), a little more with `--vacuum`.
- **Exits** 0 when done (thinned, nothing to thin, or a dry run), 2 when it couldn't run: no store, a bad flag, a `config.json` that isn't valid, or the brain running.

**The owner's calls, proposed conservatively** (#283; owner decision 60, proposed): off unless opted in, and at the start only once a data backup holds what it cuts (#284); 14 days kept whole by `npm run thin` (two weeks of 24/7 runs is several GB whole); one whole snapshot a minute, the other rows kept as stubs; no automatic VACUUM.

## Save backups

The brain backs up the game's save over the Remote File API (`getSaveFile`; architecture §6). The backups are insurance against a bug or a corrupted save (game issue #2809 is open on 3.0.1), and real starting states for the simulator.

- **When:** once on each RFA connection (the game connects on load and after a drop), and every `saveBackupIntervalMinutes` from the brain's start, over the newest open connection.
  - Before an irreversible intent goes out ([intents](#intents)), on the desired state's asking (`backupNow`).
  - One at a time: a backup asked for while one is under way follows it (several such become one).
  - With no open connection (none yet, or the last one closed), the interval's backup fails and is recorded, so a stretch with no backups shows.
  - The backups share the RFA connection with the deployer, each on its own client (request ids are unique per connection).
- **What:** the game's save at that moment, in the format Steam writes to `bitburnerSave_*.json.gz` (gzip bytes). It's a fresh save, not a copy of Steam's file. The brain checks it is what the game's own Import Game accepts before keeping it:
  - the game sent it as bytes (`binary: true`). A page without CompressionStream sends text instead, which isn't Steam's;
  - every character is a byte;
  - it gunzips into valid UTF-8, then JSON, then a `BitburnerSaveObject` with a player (`data.PlayerSave`).
- **Where:** `<data dir>/saves/<environment>/<UTC time>.json.gz`, for example `saves/E0/2026-10-27T03-30-00.000Z.json.gz` (`-` for `:`, which Windows doesn't allow).
  - Each environment has its own folder, so a simulator's or source build's backup (`E1`, `E2`) never sits beside Steam's (`E0`).
  - Each is written under a temporary name, then renamed. A half-written backup is only ever a `<name>.partial` file: it's removed when the write fails, and by the next rotation after a crash.
  - Two backups in the same millisecond: the second replaces the first.
- **Rotation:** after each backup the brain keeps the newest `saveBackupsKept` in that environment's folder and deletes the rest.
  - Only files named as backups count; anything else in the folder is left alone.
  - The backup just written is never deleted, even if the clock went back and its name sorts first.
  - An old backup that can't be deleted (in use, say) is reported as a `saveBackupRotationFailed` event, and the rest are still rotated.
- **Recorded:** every backup is a `saveBackup` event in the store, with the file (relative to the data directory) and its size, or with the failure. A failed or damaged backup is never kept. Failures include:
  - no open connection;
  - no reply in 30 s;
  - a save that isn't valid;
  - a disk error.

  Anything else is a bug, and stops the brain (fail fast).
- **Size:** the RFA server takes frames up to 128 MiB. A save reply is about twice the gzip save's size, so saves up to about 60 MB gzipped come through. A larger one would close the connection.
- **Restoring one:**
  1. **First, stop the brain, or copy the backup you want out of `saves/`.** A running brain keeps backing up whatever the game holds, on every reconnect and every interval, and rotation deletes the oldest. After a bad bug, or a corruption that still loads, that would push the good backups out.
  2. In the game: Options → Import Game, pick the `.json.gz`, then confirm. The game replaces the current save and reloads. It accepts these gzip files as they are (`src/SaveObject.ts:338-355`).
  3. When the brain runs again, the reload's RFA connection backs up the restored save.
  - **Only `E0` backups may ever go into Steam.** Saves flow one way: nothing from the simulator or a source build goes back (architecture §9.4).
  - Backups are personal data. They live in the data directory, by default the repo's gitignored `.data/`; never commit one, and keep `.data/` ignored.
- **In the simulator:** a backup loads as a save fixture as it is (`{ kind: "save", path }`), to the same state as the game's own save at that moment (`test/save-backup-round-trip.test.ts`).
- **A backup before an irreversible intent** (R8, #147): `backupNow()` takes one at once and resolves with its own event, saved or failed. Asked while one is under way, it waits for the next, so the event is never from a backup that began before the asking. The desired state's gate asks for it ([intents](#intents)).

## The data backup

What the brain can't rebuild from the game, copied so a bug, a bad thinning or a damaged disk can't lose it: the store (the campaign's history and the fast model's calibration data), `config.json`, and the newest save backup of each environment ([#284](https://github.com/UnderMyBed/bitburner-agent/issues/284), `src/data-backup.ts`). Losing the store never breaks play (architecture §7), so a backup never does either.

- **What one holds:** a folder, `<backup directory>/<UTC time>/` (`backups/` in the data directory unless `dataBackupDirectory` says), with `telemetry.sqlite`, `config.json` (with the control channel's token: keep backups as private as `.data/`), `saves/<environment>/<newest>.json.gz`, and `backup.json`, the marker naming the store it's of: its id (kept in the store's settings, `dataBackups.storeId`) and its path. A backup is this store's only if both match. A restored store keeps both; a copied data directory's store has the same id but another path, so the two are told apart (#298's re-review). The full rotation of save backups stays in `saves/`: a data backup carries the newest of each, the one you'd restore.
- **The store's copy** is SQLite's `VACUUM INTO` on a read-only connection of its own, in a worker thread (`src/data-backup-worker.ts`), never a file copy: one read transaction, so the copy is the store at one moment however the brain writes meanwhile (WAL: its writes don't wait on a reader), and compacted (no free pages). Then the copy is opened on its own and `PRAGMA quick_check`ed, the restore check: a copy that fails it isn't kept.
- **Off the event loop** (#284's measurement, `DATA_BACKUP_LARGE_STORE_MB=450` on `test/data-backup.test.ts`): a 486 MB store, written every millisecond meanwhile, was copied (454 MB) and checked in 1.7 s, with the event loop's longest delay 65 ms and 1,288 writes made during it. The same copy on the brain's own thread blocks the event loop for its whole length: 0.9 s for a 426 MB store on this PC's SSD, more on a slower disk, and longer with the check. On the brain's own connection (SQLite's online backup, `node:sqlite`'s `backup`) the brain's writes waited up to 77 ms for each step's lock.
- **When:**
  - at the brain's start, after its `brainStarted`, if one is due: none yet, or the newest older than `dataBackupIntervalHours` (24). So a crash loop's restarts don't take one each, rotating the good ones out. A backup named after now (a clock was wrong) isn't the newest: it would put the next off for as long;
  - then each time one is due, from the newest;
  - before a thinning at the start that no backup holds yet ([thinning](#thinning));
  - after a failure, again in an hour (or at the interval, if that's sooner).
  One at a time: one asked for while another is under way follows it. The due time is a timer's: a PC asleep puts a backup off (on Linux the timer's clock stops while suspended), never drops it. A store's copy that takes longer than 30 minutes (`COPY_TIMEOUT_MS`; a 486 MB store's takes 1.7 s) is a failure, so a stuck one never holds up the next, or a thinning at the start. Its worker is told to stop, but a `VACUUM INTO` already running in SQLite runs on until it ends or the brain stops, its read snapshot open and the store's write-ahead log growing meanwhile.
- **Rotation:** after each backup, this store's newest `dataBackupsKept` (2) are kept and older ones removed. Only folders named as backups with this store's marker count: anything else in the folder is left alone, so two data directories (a copy of one included) can share a backup folder without touching each other's backups. One named after now counts as the oldest: after a clock set forward and then corrected, the backups it named in the future are the first rotated out, deliberately, as the real ones are newer.
- **Never removed, so yours to delete by hand:** a folder with no marker, or one that can't be read; a partial one whose marker was never written (a crash in the moment after its folder was made); and another store's backups, a replaced store's or a moved data directory's included. The backup just written is never removed, even if the clock went back. A backup you copy back into the folder under its own name is rotated like the rest: to keep one, copy it elsewhere or rename it. Removing or renaming is tried again a few times if Windows says the file is busy (antivirus, the indexer).
- **Partial ones:** each is written as `<time>.<store id>.partial/` and renamed when it's whole and checked. A partial one is removed when it fails, and one of this store's left by a crash or a stop is removed before the next backup measures the free space. That removal is best effort: one that can't be removed (Windows, or a worker still copying after a timeout) is said in the event (`rotationFailure`, the `dataBackupFailed` alert) or, if the free space then falls short, in the failure, and the free space it takes is counted as it stands.
- **Free space:** before each, the backup's disk must keep at least 1 GB free (`MIN_FREE_BYTES_AFTER_BACKUP`) after the store, its log, `config.json` and the saves, or it fails, saying how much it needs and how much is free.
- **Disk cost:** each backup is about the store's size once compacted (a 12-hour run adds about 200 MB), so the backups take about twice the store, three times while a new one is written before the oldest goes. A 2 GB store: about 4 GB of backups, 6 GB at the peak. A thinned store keeps them smaller.
- **Recorded and logged:** each backup is a `dataBackup` event (its reason: `start`, `interval` or `thinning`; its folder, relative to the data directory when inside it; the store's copy's bytes; the saves copied; the time it took; the backups removed; and a rotation failure, if any) and a log line; a failure is a `dataBackupFailed` event (the reason and why) and a line, "data backup FAILED (at the interval): …". The dashboard's `dataBackupFailed` alert shows the newest backup's problem, a failure or older ones not removed, until one is taken cleanly or the brain restarts. The run report's section 1 lists both events and counts them, and the one a start's thinning waited for (or its failure) "(before the window)", never an earlier run's; a failed backup isn't the run's failure.
- **Stopping:** a backup under way when the brain stops is cut short with the process and records nothing; the next backup removes its partial folder.
- **Restoring the store** (or `config.json`, or a save) from a backup:
  1. Stop the brain (Ctrl+C), so nothing writes the store, and check it's stopped: `.data/brain.lock` is gone (or names no running process), and the dashboard doesn't answer.
  2. Keep the current one, its log with it: rename `.data/telemetry.sqlite`, `.data/telemetry.sqlite-wal` and `.data/telemetry.sqlite-shm` (those two if they're there) together, to `telemetry.before-restore.sqlite`, `telemetry.before-restore.sqlite-wal` and `telemetry.before-restore.sqlite-shm`. Never delete the log: after a crash it holds data not yet in the main file, and renamed with it, the kept store still opens whole. With none left, no old log can be read into the restored file.
  3. Copy `backups/<time>/telemetry.sqlite` (or your `dataBackupDirectory`'s) to `.data/telemetry.sqlite`.
  4. To restore `config.json` too, copy the backup's over `.data/config.json`.
  5. Move the backups newer than the one you restored out of the backup folder (keep them elsewhere, or delete them): the restored store is the same store to them, so the next start would take none while one is newer than the interval, and a thinning would trust a copy from before the restore.
  6. Start the brain. What was stored after the backup's time is in the renamed file, not the restored one.
  A save in a backup restores like any [save backup](#save-backups). To look at a backup first, the reports read its store as it is: `npm run report -- --data-dir .data/backups/<time>`.
- **Before a thinning at the start** (`backupBeforeThinning`): see [thinning](#thinning).

**The owner's calls, proposed conservatively** (#284; owner decision 62, proposed): 2 kept, one a day from the newest (at least an hour apart), at the start only when due, in `.data/backups/` unless configured; at least 1 GB left free; the newest save of each environment, not every save. `"dataBackupsKept": 0` turns them off, which turns thinning at the start off too. 2 kept a day apart gives 1 to 2 days to notice a problem `quick_check` can't see (bad rows), on the store's own disk by default; a third copy, or a weekly one, would widen that cheaply: the owner's call (decision 62).

  | `worldDaemonStalled` | A step on the path to the World Daemon the brain finishes in minutes, not done 5 minutes after it could be (`WORLD_DAEMON_STALLED_AFTER_MS`, #215): Daedalus's requirements met and not joined; The Red Pill reached or queued and not installed; or w0r1d_d43m0n at its level and the BitNode not destroyed (not with the destroy switched off), with what's missing. Or at once (#228, step `daedalusCount`), "Daedalus count stuck": an install while short of Daedalus's count that added none to it, passing over one that counts (#238) | When the step is done, or no longer could be (for `daedalusCount`, the next install) |

The brain plays on; a failed one is tried again within the hour | When a backup is taken cleanly, or the brain restarts (the problem is held in memory) |

  The route-stall alert (no progress on the route's critical path) needs a route, so it comes with the planner (M4).
- **Security** (owner decision 14, localhost only):
  - it listens on `127.0.0.1` only;
  - it refuses (403) a request whose `Host` isn't `127.0.0.1:<port>` or `localhost:<port>`, so a web page can't reach it by DNS rebinding;
  - it refuses (403) any request another site's page makes (`Sec-Fetch-Site`, or an `Origin` that isn't its own), so no page can even make the brain build its status;
  - it refuses (403) a `POST` without the dashboard's own `Origin`, so another page can't flip a switch;
  - the page can't be framed by another page, and everything from the brain is shown as text, never as HTML.
- **The API** (the page's; a script must follow the same rules):
  - `GET /api/status` gives the status as JSON (`src/dashboard/status.ts`, `DashboardStatus`).
  - `POST /api/supervision` with `{"paused": true}` or `{"paused": false}` sets the switch, and answers with the same. A script must send `Origin: http://127.0.0.1:12527` (with the dashboard's port) and `Content-Type: application/json`.
  - `POST /api/hack-loop` with `{"enabled": true}` or `{"enabled": false}` sets the hack loop's switch, the same way, `POST /api/programs` the hacking programs' (#136), `POST /api/home-ram` home RAM's (#138), `POST /api/cloud-servers` cloud servers' (#194), `POST /api/faction-work` the brain's faction work's (#203), `POST /api/augmentations` buying and installing augmentations' (#210), and `POST /api/world-daemon` destroying the BitNode's (#215).
  - `POST /api/intents` with `{"action": …, "args": {…}}` queues an intent (#141), answered with `{"id": …}`, or 400 with why it isn't valid. `POST /api/intents/cancel` with `{"id": …}` takes one off the queue, or 404 if it isn't there. Both the same way as the switches.
  - `POST /api/work` with `{"work": {"faction": …, "workType": …}}` sets the work (#151), or `{"work": {"kind": "company", "company": …, "field": …}}` company work (#153), or `{"work": {"kind": "crime", "crime": …}}` a crime (#156), or `{"work": {"kind": "class", "location": …, "classType": …}}` a class (#158), or with `{"work": null}` stops managing it; 400 with why for one that isn't valid.
  - Refusals:
    - 403: not the dashboard's Host or Origin;
    - 400: a body that isn't JSON, a switch's body that isn't exactly one of its two, an intent that isn't valid (or a full queue), work that isn't valid or a body without `work`, or a path that isn't valid;
    - 413: a body over 1 KiB;
    - 404: another path, or cancelling an intent that isn't in the queue;
    - 405: another method;
    - 500: the brain failed, and logs why. The server carries on.

## The hack loop

M3's first slice ([#134](https://github.com/UnderMyBed/bitburner-agent/issues/134), owner decision 34): the brain tells the Agent to run a hack loop on the game's servers (and, since #194, on its own cloud servers), and the Agent does it ([`packages/ingame`](../ingame/README.md#the-hack-loop)). It's the first desired state (architecture D2), and the code is `src/hack-loop.ts`.

- **The switch:** on unless the owner turns it off on the dashboard. It's the store's setting `hackLoop.enabled`, so it survives restarts of the brain. Off is sent at once, and the Agent stops every loop at its next round: within two rounds (4 s).
- **The target** (`chooseHackTarget`): a starter rule, until the planner (M4) decides.
  - Among the game's rooted servers with money (never home, a Hacknet server or one the player bought) that need at most half the player's hacking level (at least 1), it takes the one with the highest maximum money times growth.
  - Growth counts because the loop hacks only once a server's money is back at 75% of its maximum, and servers start at 4%. Over an 8 GB fresh start's first virtual hour, n00dles (growth 3000) earned $15m. foodnstuff, joesguns and sigma-cosmetics, with more money but growth 5–20, earned nothing.
- **The hosts** (`hackLoopHosts`, [#194](https://github.com/UnderMyBed/bitburner-agent/issues/194)): the rooted servers with RAM in the medium snapshot that are the game's own (the static snapshot's, not purchased: never home, which is the Agent's, nor a Hacknet server, whose RAM makes hashes), and the brain's own [cloud servers](#cloud-servers) (`pserv-<n>`, core's `isBrainCloudServerName`). Those are hosts from the first medium snapshot after they're bought (10 s), at their RAM after an upgrade. The owner's own cloud servers, under any other name, are never hosts: the owner uses them (#134). It's the one place that says where the loop runs: the plan, the cloud server rule and the run report read it, and so does A1's hacking ceiling (#196).
- **The move to the next target** (`planHackLoop`, [#184](https://github.com/UnderMyBed/bitburner-agent/issues/184)): on Steam, `7990834`'s loop moved every host from n00dles to zer0 when hacking reached 150, with zer0 at 4% of its money. The loop hacks only at 75% of the maximum and within 5 of the minimum security, so every thread weakened and grew it, and money stayed flat for 24 minutes until the owner stopped it. Now:
  - `best` is the starter rule's target. `current` is the target last set while it's still a candidate, across the Agent's reconnects while the game hasn't reset (the slow snapshot's `lastAugReset`). With none (a brain restart, the switch turned on, or a reset), it's the best candidate that's **ready**; else the one with the most of its money, of its maximum, if more than a fresh start's 4% (Server.ts:74-75): that's the one being worked, caught between a hack and its weaken; else `best`. Judged afresh on a reconnect, a target between a hack and its weaken isn't ready, and every host would have moved to the next target, the Steam stall again (#184 review).
  - **Ready** is the loop's own thresholds, in core (`isHackLoopReady`, `HACK_LOOP_MONEY_FRACTION`, `HACK_LOOP_SECURITY_MARGIN`), which `hack-loop.js` uses too: the medium snapshot's money at least 75% of the maximum, and security at most the minimum + 5.
  - `current` **earns** once a medium snapshot has shown it ready since it became the target (the loop has hacked it), or when it was taken as the one being worked.
  - `best` is `current`, or ready, or `current` doesn't earn yet: every host goes on `best`. Nothing earning is given up.
  - Otherwise `current` keeps earning on most hosts, and the largest, in RAM order (ties by name), **prepare** `best` until they hold at least half the hosts' RAM. Preparing is the same loop: it weakens and grows `best`, and hacks once it's ready. With two hosts or more, some are always left to earn. The hosts that prepared last time stay while they still hold at least half the RAM and leave some to earn, so a larger host rooted since doesn't stop a weaken or grow under way. With no host at all, nothing is prepared. The next medium snapshot that shows `best` ready moves every host to it.
  - The rule may move on while a target is prepared. In the simulator, zer0 was still being prepared when max-hardware became `best` at about hacking 160, and the loop moved from n00dles to max-hardware.
- **Each host's hack threads** (`hackThreads`, [#187](https://github.com/UnderMyBed/bitburner-agent/issues/187)): the loop hacks once money is at 75% of the maximum, so every host's loop sees that at about the same time and hacks together. With all their threads, they took max-hardware from $124m to $111 in the simulator, and its growth of 30 took 25 minutes to bring it back. So the brain gives each host, earning or preparing, the threads its loop hacks with:
  - **The rule:** a round of hacks by every host takes no more than `HACK_REGROW_ROUNDS` (2) rounds of their grows bring back. A round of grows multiplies the target's money by e^g: g is the hosts' threads (their RAM over the loop's 2.4 GB budget, core's `HACK_LOOP_RAM_BUDGET_GB`) times one thread's log of growth at the target's minimum security plus 5, the slowest the loop lets it grow (core's `growthLogPerThread`, the game's `calculateServerGrowthLog`, grow.ts:8-28). A host's hack with t threads keeps 1 − t × p of what it finds, p being one thread's share at the target's minimum security, the most it ever is (core's `percentMoneyHackedPerThread`, the game's `calculatePercentMoneyHacked`, Hacking.ts:44-57). Each host's part of 2g is its part of the RAM, G, and its threads are the most whose hack keeps at least e^−G: (1 − e^−G) / p. Together the hosts' hacks keep at least e^−2g.
  - **n00dles** (growth 3000) grows back from anything: every host's count is over its threads, so all of them hack, as before. **zer0 or max-hardware** (growth 30 to 40): a fraction.
  - **Each count** is at least 1, then rounded down to a power of two, so the share's slow rise with the hacking level changes it, and restarts that host's loop, only now and then. Then it's at most the threads the host's RAM holds (n00dles's count is all of them), still at least 1. A count over the loop's threads (RAM used by other scripts), the deploy worker caps.
  - **BitNode multipliers** aren't in core yet: `ScriptHackMoney` and `ServerGrowthRate` are taken as 1. That's exact in BN1. Elsewhere both are at most 1 (BitNode.tsx): the share per thread is then overestimated (fewer hack threads, safe), and so is the growth. In BN2 (0.8), BN3 and BN11 (0.2) that makes the counts up to 5× too generous, the unsafe side; it's to revisit when BitNode multipliers come to core. The player's `hacking_money` and `hacking_grow` multipliers come from the medium snapshot, 1 where it doesn't say.
  - **Why 2:** see [the income suite](#the-income-suite).
- **The controller** (`DesiredStateController`, `src/desired-state.ts`; since #151 it also sends [work](#work); since #141 it also sends [intents](#intents): [the hacking programs](#the-hacking-programs), [home's RAM](#home-ram), [cloud servers](#cloud-servers), [the backdoors](#backdoors-for-the-hacker-factions), [the joins](#factions-and-their-work) and the owner's manual queue) keeps the control channel's desired state in step with the switches and the connected Agent's snapshots:
  - **Off** is sent at once, to each Agent as it connects too.
  - **On** waits for that Agent's own static and medium snapshots, which come in its first round, then sends the target (or none yet, while the servers get rooted) and the hosts. It never sends the last brain's or the last game's view:
    - a brain that restarts sends the running Agent the same state, which changes nothing;
    - an Agent after a reset is never given a target its game can't hack.
  - It keeps the target it last set, whether it earns, and the hosts preparing the next one, for the move to the next target (#184): across the Agent's connections while `lastAugReset` is unchanged. It forgets them on a reset or the switch off; a new brain starts without them.
  - The channel sends each connection a state once, then again on a change. It sends only to a welcomed Agent running the deployed code. While the brain holds, it sends only what starts nothing new: the hack loop off, or as last sent, and no intents or work ([protocol](../../docs/bridge/protocol.md#rules)).
  - The dashboard shows the controller's own view: on or off, waiting for the snapshots, the target and the number of hosts, and the target being prepared with its number of hosts, each with its hosts' hack threads added up (#187).
- **Wiring:** `main.ts` makes the controller before the control channel listens, with the save backups it asks before an irreversible intent, and the brain's log for the backdoors' lines (#195) and the factions' (#203); the faction rule's events go to the store through `recordEvents(desiredState, …)`, as the deployer's do. The simulator suite wires it the same way through `test/helpers/brain-in-simulation.ts` (`withDesiredState`). `brain-process.test.ts` doesn't cover it.
- **The suite** (`test/hack-loop-skeleton.test.ts`), in an 8 GB fresh start in the simulator:
  - The Agent roots the no-port servers and runs the loop on each against the brain's target (n00dles). The money grows by over $500,000 in 10 virtual minutes.
  - An owner's script already on foodnstuff is untouched, and the loop there has only the RAM it left.
  - Home never holds more than the Agent and one worker, the hack loop's included.
  - **A loop killed from outside** is back within one convergence (30 s) and a round.
  - **Off,** every loop is gone within two rounds and stays gone. On again, they're back.
  - **A brain restart** leaves the loops alone: the very same processes.
  - **After a disconnect,** once connected again, the Agent acts only on that brain's instructions. From a brain that sends none, a loop that stops stays stopped. (With no brain at all, it's [safe mode](#safe-mode).)
  - **With the desired state set directly:** only the named hosts run the loop, a new target restarts the loops against it, a dropped host's loop goes, and another deployment's loop is stopped.
  - **Each host its own target** (#184): five hosts earn on n00dles while foodnstuff and joesguns prepare joesguns. When all move to joesguns, only the five loops against n00dles are stopped and started, and the owner's script on foodnstuff is untouched. The Agent's log names both while preparing: "on, N threads (H hacking) on 5 servers, against n00dles; preparing joesguns on 2 servers (H hacking)".
  - **Each host's hack threads** (#187): a count over a host's loop threads is capped at them; a host the state doesn't name hacks with all its threads; a changed count, or a first count for a host that had none (as from an older safe-mode file), restarts that host's loop alone, and the others keep their pids; the Agent's log gives the threads hacking. With 13 threads hacking in all (1 to 6 a host), the hosts' hacks never take n00dles below 70% of its money once it's at 75%: `hack`'s `threads` option at work, in the game's own code. (All 37 threads would take about 15% a round, to about 64%: arithmetic, not something the test runs.)
  - **Home too full for the deploy worker:** home never holds more than the Agent, the owner's script and one worker, and the deploy worker runs within two rounds of there being room.
  - **A purchase the page can't make** (#136; the simulator's page has no sidebar): each try logs why, the next comes 30 s later, and home never holds more than the Agent and one worker. E2 buys on the real page ([packages/e2](../e2/README.md)).
  - **A home RAM upgrade already made** (#138; an upgrade from 4 GB on the fresh start's 8 GB): the worker reports it done from the game alone, without touching the page, so a repeat never buys a second doubling.

## The hacking ceiling

"How good is our hacking" as a number (#196, M4 phase A slice A1): the most hacking income a second that RAM could earn at the player's hacking now, from the game's formulas, against what hacking actually earned. Two ceilings, both upper bounds:

- **The batcher ceiling, the score** the batcher (A7) is judged on: a batcher (HWGW) commits its grow and weaken threads before it knows whether the hack lands, so a failed hack wastes them.
- **The hacking ceiling,** reached only by a reactive hacker that grows and weakens just what a landed hack took. Nothing passes it.

**Per GB-second** (core's `batcherIncomePerGigabyteSecond` and `hackingIncomePerGigabyteSecond`, `packages/core/src/hacking-ceiling.ts`). On a target at its minimum security and maximum money M, where every figure is at its best, each dollar hacked costs at least:
- **hack:** 1/(c·p·M) threads of a 1.7 GB script for T, failed hacks included. c is the chance (`hackChance`, Hacking.ts:9-24), p one thread's share (`percentMoneyHackedPerThread`, Hacking.ts:44-57), and T the hack time (`hackTimeSeconds`, Hacking.ts:60-80).
- **grow:** 1/(M·k + 1) threads of a 1.75 GB script for 3.2T, k being one thread's growth log with the core bonus (`growthLogPerThread`, grow.ts:8-29; ServerHelpers.ts:287-290). Growing a share f back takes x threads with (M(1 − f) + x)·e^(kx) = M (grow.ts:38-58). With u = x/M − f, that is kx = −log(1 + u) ≥ −u, so x·(k + 1/M) ≥ f, with equality only as f → 0.
- **weaken:** removes what the hack adds (0.002 a successful thread) and what the grow adds (0.004 a thread) (Constants.ts:9; ServerHelpers.ts:209-211), at 0.05 × the core bonus a thread (Constants.ts:10), with a 1.75 GB script for 4T.

**Why the limit is the best over f:** the hack and its weaken cost the same per dollar at any share f, and grow costs more as f grows, so the cheapest batch is the one at f → 0.

**The batcher ceiling** divides the grow and weaken terms by c too. On zer0 at hacking 150 that is about 68% of the hacking ceiling. A whole-thread HWGW batch at f = 5–10% comes within 15% of the batcher ceiling, and never above it.

The script RAM is the game's (RamCostGenerator.ts:11-20). A host's usable RAM counts whole threads (`usableRamGb`): floor(RAM/1.7) threads at 1.75 GB each, at most its RAM, so a 2 GB host gives 1.75 GB.

**What both assume, and so ignore:**
- continuous batching with no gaps, every operation landing on time, and fractional threads within a host;
- security and money held at their best;
- the hosts' whole RAM free, and the best cores among them applied to all of it (loose where cores differ);
- one target at a time;
- the hacking level as the snapshot has it.

**BitNode multipliers** are taken as 1. That is exact in BN1. Elsewhere `ScriptHackMoney`, `ScriptHackMoneyGain`, `ServerGrowthRate` and `HackingSpeedMultiplier` are at most 1, so the ceilings err high, the safe side. BN11's `ServerWeakenRate` of 2 errs low (BitNode.tsx:896).

**Over the snapshots** (`hackingCeiling`, `src/hacking-ceiling.ts`). The targets are the game's servers rooted, with money:
- **The score** uses the RAM the brain's hacking uses: the hack loop's hosts (`chooseHackHosts`, `hackLoopHosts`'s names: the cloud servers among them since #194, and A7's later). It gives the best target's batcher ceiling, and beside it the hacking ceiling.
- **The bound** uses all the RAM a script could run on: every rooted server, including home and the cloud and Hacknet servers. It gives the best target's hacking ceiling. The owner's scripts, a terminal `hack`, or A7 on home all count in what hacking earns, so all that RAM counts here.
- **Unknown, with the reason,** when either snapshot is missing, or the player's skills (`hacking`, `intelligence`) or multipliers (`hacking_chance`, `hacking_speed`, `hacking_money`, `hacking_grow`).
- **Each target's batcher income on the hosts' RAM** (#275, given `incomes`): its batcher ceiling a GB times the hosts' RAM, at most what batches can take from its money (core's `batchIncomeMostPerSecond`). The run report keeps them a medium snapshot at a time (`HackingFold`'s `targetIncomes`, by index into one list of names: a 14-hour store's 5,000 medium snapshots), for section 6's stuck target check.

**What hacking earned:** the slow snapshot's `moneySources` (#196), which is `ns.getMoneySources().sinceInstall`. Its `hacking` field counts every hack's money (NetscriptHelpers.tsx:599).
- **Between slow snapshots** it is the rise in that count.
- **After an install** (`resetInfo.lastAugReset` changed; the install resets the count), what the count says is what was earned since.
- **A fall with no install** is a relaunch, which loads the save's older count. That interval counts as nothing earned.
- **Why not money's rises:** they would count crime and work, and purchases would hide hacking.

**The dashboard's rows:** "Hacking ceiling" and "Hacking income". The income row shows the last 10 minutes as percentages of both ceilings now. The brain sends their text, the same words the run report uses.

**The run report's section 5** (`HackingFold`, fed by the run report's own pass over the store: static, slow, then medium snapshots):
- **The ceilings:** each medium snapshot's ceilings, with the static snapshot in force then, stepped across each interval between slow snapshots. A window that starts after the Agent's static snapshot takes the one before it (`latestSnapshotBefore`).
- **The headline is the best 10 minutes:** hacking's percentage of the batcher ceiling, the stretch A7 is judged on. Preparing a target and switching between targets mean no run comes near 100% over a whole window.
- **Then the window and each hour** against both ceilings, and the ceilings now.
- **Under each hour, what held the cycle back** (#245, `BitNodeCycles.heldBackBetween`; under the window's line with an hour or less): 2b's judgements made in the hour, by time online, the most first, answers tied for the most named together ("reputation and factions equally"). Run #3's BN1.2 read as a failure at "0.1% of the batcher ceiling" for hours in which reputation held the cycle back and up to $766,000,000,000,000 went unspent. Where the most is reputation, the count or the brain's own state, it says income wasn't it, with the most money the judgements giving that answer saw (each judgement's own medium figure, so an hour across a destroy never quotes the BitNode before's): "held back by reputation, not income (92% of 55 min online judged in the hour; count 8%); most money unspent $766,000,000,000,000". Where money is among them, "held back by money: income (…)" ("reputation and money: income"). "factions" makes neither claim, as joining one can cost a travel. Or "not judged in the hour" and why. A judgement counts in the hour it was made, its time online to the next judgement with it.
- **Not judged:** intervals where the ceilings were unknown; the section says for how long.
- **A failure:** hacking earned more over the window than the bound's $ allow. The bound's $ are the ceiling on all rooted RAM, plus what the game's servers' money fell by between relaunches and installs (money they held at the start, hacked and not grown back, which no RAM paid for). This means the formula, or the measure, is wrong.
- **Not allowed for, known slack:** security left above where it started, which is the same kind of debt; and hacks finishing early in the window that started before it, a few minutes' worth.
- **A floor since #206:** the score suite (`test/batcher-score.test.ts`) holds the batcher to `LEAST_SCORE`, 24.5% of the batcher ceiling, and above the hack loop on the same seed.

## Sharing spare RAM

M4 phase A ([#224](https://github.com/UnderMyBed/bitburner-agent/issues/224), epic #191): `ns.share()` raises the reputation all faction work earns while its threads run (10 s a call): hacking work's by its bonus, 1 + ln(1 + the threads × an intelligence and a core bonus)/25, field and security work's hacking and intelligence term only, with SF15.3's charisma in field's (`NetworkShare/Share.ts`, `PersonObjects/formulas/reputation.ts:16-52`; core's [share](../core/README.md#sharing-spare-ram)). The first overnight run (2026-10-31) ended with $157t unspent, reputation the bottleneck, and most of its 26 PB idle. `src/share.ts`, sent by `DesiredStateController`; the batcher does the sharing ([packages/ingame](../ingame/README.md#the-batcher)).
- **The switch:** the dashboard's "Stop sharing spare RAM" (`share.enabled`, `POST /api/share`), on by default ([owner decision 52](../../docs/decisions/owner-decisions.md)).
- **When:** while the player works for a faction: the work sent (the owner's on the dashboard, or the brain's own, #203) is faction work and the Agent's fast snapshot says the game showed it (`factionWorkGoingOn`; the game's `getPlayer()` has no current work, NetscriptFunctions.ts:1417-1436, so work the owner starts in the game by hand, with none set, isn't seen), with the batcher sent. With the batcher off, nothing shares: the hack loop's hosts are its own. The brain adds `sharing` to the batcher's config; the work over, it's gone at the next medium snapshot, and the batcher's last round ends within 10 s. ## Cloud servers

M4 phase A's A2 ([#194](https://github.com/UnderMyBed/bitburner-agent/issues/194), epic #191, owner decision 46): the brain buys and upgrades cloud servers by a payback rule computed from the game's prices and the hack loop's measured income, and the hack loop runs on them ([the hosts](#the-hack-loop)). The Agent buys through the NS API, with no page ([`packages/ingame`](../ingame/README.md#buying-servers)). The code is `src/cloud-servers.ts`.

- **The switch:** "Stop buying cloud servers" on the dashboard ("Start buying cloud servers" when off), on unless the owner turns it off (the store's `cloudServers.enabled`), like the others. Nothing is bought with the hack loop switched off: cloud servers only run it.
- **The game's prices** (BN1, `Server/ServerPurchases.ts:23-54`, `Server/data/Constants.ts:4,12-13`): $55,000 a GB at every size (`CloudServerSoftcap` is 1), so an 8 GB server is $440k and 1 TB $56.3m; an upgrade costs the difference between the two sizes' prices, the same per GB added. At most 25 servers, of up to 2^20 GB. Other BitNodes multiply the price, the limit and the most RAM (`BitNode/BitNode.tsx`): there nothing is bought, and the dashboard says the prices aren't known yet. Nothing either until the Agent's slow snapshot says which BitNode.
- **Income per GB** (`HackLoopIncome`): from the connected Agent's medium snapshots, money's rises added up (a purchase lowers money, which isn't income), over the hack loop's hosts' RAM × time (`hackLoopHosts`, each stretch at the RAM the snapshot that starts it shows), across the last 10 minutes (`CLOUD_SERVER_INCOME_WINDOW_MS`). Nothing is bought until the snapshots span the window, and a disconnect starts it again. Money from work (crime, a company job) counts too, which errs toward buying.
- **The next purchase** (`chooseCloudServerPurchase`):
  - **Where:** under the game's limit of 25 (the owner's own cloud servers count toward it), a new server, `pserv-<n>`, the least n no server's name is or starts with followed by `-` (so a purchase the game renamed, `pserv-1-0`, makes the brain pass `pserv-1` over rather than buy it again and again); at the limit, the smallest of the brain's own (ties to the first name), upgraded. The owner's own cloud servers, under any other name, are never upgraded; with all 25 the owner's, the dashboard says there's no room.
  - **What it trusts:** a server's RAM must be a positive number to count, and a RAM the game sells (a power of two) to be upgraded from; hostnames must be strings. Snapshot data is the Agent's word.
  - **How much:** the largest power of two of RAM, at least 8 GB for a new server (three of the loop's 2.4 GB threads), whose price money covers, less the reserve, and whose **payback**, its price over the RAM it adds times the income per GB a second, is within `CLOUD_SERVER_PAYBACK_LIMIT_MS` (15 minutes). In BN1 a GB costs the same at every size, so the payback is too: the rule buys the largest money allows, or nothing.
  - **Kept in flight:** the purchase last sent is sent again while it's still to do and money and payback still allow it, so its id (and the Agent's count of tries) holds as money rises, and a purchase that keeps failing reaches `intentStuck`.
- **Order and reserve** (`DesiredStateController`): one purchase at a time. A program or home RAM upgrade the money covers goes first, and the dashboard says the cloud server waits for it. While the cheaper of the two waits for money, its price is held back from cloud servers if the hack loop's income would bring what's still short of it within `CLOUD_SERVER_RESERVE_HORIZON_MS` (1 minute): it's nearly there, so it's bought first. One further off isn't held back (SQLInject.exe's $250m, a large home RAM upgrade): cloud servers raise the income that brings it nearer, and once they stop paying back, money gathers for it anyway.
- **Sent as an intent** (#141): `buyServer { hostname, ram }` (#159), or `upgradeServer { hostname, ram }` (#194), after the programs' and home RAM's.
- **Fail loudly:**
  - A purchase not done after 5 tries is `intentStuck`, and fails the run report, as any intent.
  - A purchase the Agent reports done with a problem (bought under another name) is noted, raises `cloudServerProblem`, and stops the rule: the dashboard says it waits for you, and turning the switch off and on again goes on. The run report fails on it. The note is the brain's, in memory: a restarted brain buys again (the report still fails on the purchase that went wrong). A purchase not done, with a problem ("not enough money"), is tried again, and isn't noted.
- **The dashboard** shows the purchase being made, its RAM, price and payback, or what it waits for, and the cloud servers with their RAM.
- **The run report** gives the fleet a line a cycle (with `--verbose`, each cloud server bought or upgraded, with its RAM and price), and the hack loop's hosts' RAM, first snapshot → last in each BitNode ([the run report](#the-run-report)).

While it waits there, the first other invitation from a faction without enemies is joined beside it, so a long wait (backups failing, say) holds up no join that bans nothing; the factions panel says so ("Joining: Sector-12; CyberSec beside it, a join with enemies"), and the log as it starts and ends.
- **Working** (`chooseFactionWork`), from the slow snapshot's faction state and reset info, and the medium snapshot's player:
  - **Worth having:** an augmentation's hacking value is core's `hackingValue` at the player's hacking level: the logarithms of its speed, money, growth, chance, experience and faction reputation multipliers added up, and its hacking skill multiplier as the experience multiplier that lifts the level as much at that level (`hackingSkillValue`), so a skill augmentation counts for more as the level climbs. One with none (combat, The Red Pill) isn't worked for; NeuroFlux Governor is left to A6.
  - **The candidates:** each augmentation a joined faction that offers work sells, with a hacking value, neither installed nor queued, each missing prerequisite sold by a joined faction, and its reputation (core's `augmentationCost`, the BitNode's multiplier in) not yet reached at any joined faction that sells it: one reached is A6's to buy.
  - **The rate:** each faction's best work type by the game's formula (core's `factionReputationPerSecond`): the player's skills and `faction_rep`, the faction's favour, and the focus the work goes with (decision 37).
  - **The choice:** the most hacking value per second of work to reach the reputation; ties to the sooner, then the faction first in the game's order. It's stable: working for a faction only brings its candidates nearer, and once one's reached the next is chosen, usually at the same faction, which changes nothing sent.
  - **Short of Daedalus's count** (#228, core's `daedalusCountOf`): every augmentation but NeuroFlux Governor and The Red Pill is a candidate (each adds one to the count). Those with a hacking value still go first, by value a second (they count too, and the early game stays as above: the brain's reading of #228); with none left to work for, the soonest reached of the rest, the work saying it's for the count ("…, for Daedalus's count: 23 of 30 augmentations installed").
  - **The Red Pill first** (#215, [the World Daemon](#the-world-daemon), `redPillWork`, core's since #260): once a joined faction sells it (Daedalus), it's neither installed nor queued, and no joined seller's reputation reaches it, the work is the seller's best, for The Red Pill, ahead of any hacking value: it ends the BitNode.
  - **Sent** as the work (`{ faction, workType }`, focused per decision 37) when the owner has set none and the switch for **the brain's faction work** (`factionWork.enabled`, on unless turned off) is on. The owner's work always wins. The Work view says whose the work is (`source`: `owner` or `brain`).
  - **None** when the snapshots don't say yet (none, the faction state unread, a figure missing): no work is sent, so the Agent leaves the game's work as it is. Or definitely: no faction joined, none that offers work, nothing left worth it, or an augmentation core doesn't know (another game version).
- **The brain's log:** "factions: joining CyberSec (its invitation)", "factions: CyberSec joined"; "faction work: hacking for CyberSec, for Neurotrainer I (reputation 2 of 1,000, 0.32/s: about 52 min)" at each new choice; "faction work: stopped (your work on the dashboard)" when a definite reason ends it.
- **Events, for the run report:** each choice as a `factionWorkChosen` event (the faction, work type, target, reputation, requirement, rate and ETA) when its faction, work type or target changes, and its end as `factionWorkStopped` (`{ reason }`). Snapshots missing (a reconnect) store nothing. The controller's clock for them is the latest channel event's time.
- **Fail loudly:** a join that fails is an intent not done: after 5 tries, `intentStuck`. While the brain's work is sent, its faction's reputation is watched in the connected Agent's slow snapshots: risen under half the work's rate (`FACTION_WORK_ON_TRACK_SHARE`) across the last 10 minutes (`underRateSince`), it's the `factionWorkStalled` alert and a "faction work STALLED" log line ("… rising at the work's rate again" when it recovers). Not any rise: a joined faction not being worked gains passively (`Faction/FactionHelpers.tsx:132-170`), at most a tenth of the best work's rate, or 1/120 a cycle. Judged over the whole window, not snapshot to snapshot: the page's reader (#197) reads the worked faction's reputation fresh each time from the work's own display, but any other faction's only when it opens the Factions page, at least every 10 minutes; work that isn't going on leaves a reading that stays flat, then jumps by up to 10 minutes of passive gain, which one interval alone could take for work. The run report fails on the same stretches ([the run report](#the-run-report)).
- **The BitNode's `FactionWorkRepGain`** (0.2 in BN14, 0.5 in BN2) is in the rate, from core's table: the stall compares against it, so it must be the game's.
- **Working toward donation favour** (#225, [owner decision 53](../../docs/decisions/owner-decisions.md), legacy `work-for-factions.js:897-918`, `:929-930`; `workTarget`, core's since #260): at a faction that takes donations (core's `acceptsDonations`), the work goes to the lesser of the augmentation's reputation and the reputation this cycle that unlocks the faction's donations at the next install (core's `reputationToUnlockDonations`: 462,491 from no favour in BN1), unless the augmentation's is within 10% of the larger of that and the reputation now (`WORK_TO_AUGMENTATION_WITHIN`): then all the way to it. Past the target, the augmentation is bought with a donation after the install. The ETA and the value a second use the target.
  - **Unlocked:** a faction whose donations are unlocked isn't worked, nor an augmentation one sells: A6 buys its reputation.
  - **The Augmentations switch off:** no install or donation follows, so none of this applies: each augmentation is worked to its own reputation, at any faction.
  - **The Red Pill** stays first, worked to Daedalus's target the same way, and not at all once Daedalus's reputation reaches it (A6 installs for "Daedalus donations") or its donations are unlocked (A8's way donates).
  - **The choice in words** says the target and why: "hacking for BitRunners, for BitRunners Neurolink (reputation 400,000 of 462,491: donations at the next install, BitRunners Neurolink at 875,000; favour 0.0, 150.0 after the next install at it, …)". Its event carries `target`, `augmentationReputation` and `favor`, and a change of target is a new choice.
- **The share bonus** (#224): the rate counts the bonus of the share threads the batcher reports running (`shareBonusOf`, [sharing spare RAM](#sharing-spare-ram)), so the choice, its ETA and the stall's rate include it; 1 with none.
- **Not modelled:** a gang's faction (none in BN1: the shops are asked with no gang, so a gang's would be its faction's own list).

## Augmentations and the reset

M4 phase A's sixth slice ([#210](https://github.com/UnderMyBed/bitburner-agent/issues/210), epic #191): the brain buys the augmentations worth installing and installs them, the run's reset cycle. Its choices are computed from the game's formulas (owner decision 46), in core's `augmentation-plan.ts` ([`packages/core`](../core/README.md#augmentations-and-the-reset)). The rule, as the controller runs it, is `src/augmentations.ts`; what the run report reads of it is `src/augmentation-report.ts`. **It's on by default, so a live run resets** (owner decision 48). The dashboard's Augmentations switch (`augmentations.enabled`, `POST /api/augmentations`) turns it off. Since #260 the decision before the commit is core's (`augmentationShops`, `augmentationEndgame`, `installJudgement`, [core](../core/README.md#the-brains-choices-shared-with-the-fast-model)), shared with the fast model; the rule here keeps the countdown, the commit, the purchases and the words. What of these the fast model copies is tested against the brain on the same inputs (#263, "brain against the fast model"): in `test/augmentations.test.ts`, the countdown's start, extensions, end and call-off, the countdown's and the lookahead's reserves, #243's hold with its window and `assumeMoney`, and the copied constants; in `test/desired-state.test.ts`, the purchase chosen (a program, home RAM or a cloud server) from the same purse, money and income, and what the countdown and the endgame holds hold back from it; since #294, in `test/cloud-servers.test.ts`, the cloud purchases' income measure, sample by sample, and in `test/backdoors.test.ts`, a hacker faction's join: `BackdoorRule` asking on the Agent's medium snapshots, one server at a time, and `chooseJoin` picking the joins' order at slow snapshots, on the Agent's and the game's clocks, within 0.3 s of the model's mean; with the constants the model copies read from their sources.

- **What it reads:**
  - from the slow snapshot: the faction state (#197: each joined faction's reputation and favour, and the queue), the reset info (the installed augmentations, the BitNode, the Source-Files, `lastAugReset`), its game time, and the money sources since the install (`moneySources`, for the income);
  - from the medium snapshot: the player (skills, money, `faction_rep`) and home's RAM.

  Without one of them it waits, saying which. Nothing is decided on a guess.
- **Not committed, each update:**
  - **Reached:** each augmentation a joined faction sells (not NeuroFlux Governor), neither installed nor queued, whose reputation a joined seller has; or (#225, [donations](#augmentations-and-the-reset)) one a joined faction with donations unlocked sells, counted when the money covers its price and its donation.
  - **The set:** core's `chooseAugmentationsToBuy`, the most hacking value (A5's `hackingValue` at the hacking level, #203) the money covers. It's chosen greedily, each augmentation with its prerequisites, in buy order: dear ones early, since each purchase makes the next 1.9 times dearer (`Constants.ts:41`), but a prerequisite before what needs it, and a prerequisite chain by its dearest member (so a cheap prerequisite of a dear augmentation goes first, its chain right after).
    - Only augmentations worth installing count: those with a hacking, speed, money, growth, chance, exp or faction reputation multiplier.
    - So no combat or charisma augmentations, and no The Red Pill (A8's); but short of Daedalus's count (#228, [below](#invitations-and-daedaluss-count)), any but NeuroFlux Governor and The Red Pill.
  - **When to install: the legacy scripts' count rule** (#222, [owner decision 51](../../docs/decisions/owner-decisions.md), replacing #210's comparison of the next augmentation's times, which waited all through the first overnight run). It's core's `installRule`, from `alainbryden/bitburner-scripts`' autopilot.js (`maybeInstallAugmentations`); smarter timing is phase B's planner's (decision 46).
    - **The counts:** *affordable*, those worth installing that an install would really install (the faction state's queue and the purchases reported done it doesn't show yet, never one `augmentationNotQueued`, #222 review) plus the set; *with NeuroFlux*, that plus NeuroFlux Governor's queued copies and the levels the money left after the set covers at the joined sellers' most reputation (core's `affordableCounts`, each level priced after the last).
    - **The bars:** install at 8 affordable, or 12 with NeuroFlux. Each falls by `floor(0.5 × hours online this cycle)`, never below 1: 7 and 11 from 2 h, the bar 1 from 14 h, with NeuroFlux from 22 h.
    - **A quick install:** under 20 minutes into the cycle (online and in the game's time, so a save first seen mid-cycle isn't one), 4 with NeuroFlux.
    - **Nothing left:** no augmentation worth installing left unowned at the joined factions beyond the set, with something to install (#210's, kept).
    - **Never**, for any reason, with nothing really to install: nothing queued, in the set or among the levels to buy. So a purchase never queued can't keep choosing installs at a bar of 1 (#213's never-chosen-again guarantee). Left out of the legacy scripts', each the planner's: SF11's +1 a level (BN11), a gang's 6 for a quick install, and BN8's and BN9's overrides.
  - **The bars' clock: the game's time online this cycle** (`advanceOnlineClock`): the time between consecutive slow snapshots of the same `lastAugReset` no more than `AUGMENTATION_SLOW_GAP_MS` apart (3 slow intervals, 3 minutes: more is the game closed, or the Agent or the brain away). Never the game's time since the install, which counted the save's 95 h closed before the first overnight run. It's kept in the store (`augmentations.online`, keyed by `lastAugReset`), so a restarted brain carries it on; another `lastAugReset` starts it at 0, and so does a save first seen mid-cycle: the conservative side, the bars at 8 and 12. A gap, or the game's clock set back, is left out and logged. There's no NS call for the time online (`getTimeSinceLastAug` went in 3.0).
  - **The countdown:** once the rule says install, the brain doesn't commit at once. It starts a countdown in the game's time (the latest snapshot's): 90 s, 30 s for a quick install. Meanwhile the money the counted purchases cost (the set and the NeuroFlux levels) is held back from cloud servers and home RAM, as the legacy scripts' reserve.txt holds it, and no program is bought (lost at the install). Each rise in the count with NeuroFlux extends it to `max(10 s, countdown × (1 − extensions ÷ the bar with NeuroFlux))` from now, never shortening it. If the rule stops saying install, it's called off; so it is by The Red Pill's way, a hold for Daedalus's count (#243), the switch, a reset, or the game's clock set back (a save loaded: a fresh one starts from the new time). The Red Pill has none. Each start, extension, call-off and end is logged ("augmentations: install countdown started, 90 s, the count reached: 8 of 8 new augmentations affordable (8 of 12 with NeuroFlux); $2,927,417,203 held back from cloud servers and home RAM").
  - **The progress:** each change in a bar, the reason, the countdown's end or a hold is an `augmentationProgress` event at once (the counts, both bars, the time online, when each bar falls next, the countdown, the hold); a change in the counts alone at most every `AUGMENTATION_PROGRESS_COUNTS_EVERY_MS` (5 minutes: money see-sawing across a NeuroFlux price would record each crossing); a steady state records nothing. The dashboard shows the same.
  - **The income** is the rise in `moneySources.sinceInstall`'s earnings (hacking, work, crime, Hacknet, contracts, infiltration) over 10 minutes of slow snapshots with no gap, for the reserve's lookahead alone (below).
  - **Chosen** at the countdown's end: the commit is kept in the store (`augmentations.cycle`, the `lastAugReset` it was chosen in) until a slow snapshot shows another, so a restarted brain carries on. The choice is an `augmentationInstallChosen` event (the set and its money, what's queued, the time online, the counts, the bars, and why: `count reached`, `quick install`, `nothing left`, `The Red Pill` or, #225, `Daedalus donations`) and a log line: "augmentations: install chosen, 6.0 h online this cycle: buying …, the count reached: 5 of 5 new augmentations affordable (7 of 9 with NeuroFlux)". Short of Daedalus's count, the note also keeps the facts of what counts within reach then (`countFacts`, #238): the money left after the set, and what counts within reach beyond it, the World Daemon's for "Daedalus count stuck".
- **Committed, one intent at a time,** each with its source `augmentation` in the intents list:
  0. **The note's donations** (#225), one faction at a time, The Red Pill's first, each shown by the faction state before anything else is asked for (below).
  1. **The set's next purchase** (`purchaseAugmentation`, #149), from the joined seller with the most reputation. The set is recomputed from the queue each time.
  2. **Home's RAM,** an upgrade at a time while the money covers it and its switch is on, but only with the money above the NeuroFlux Governor levels counted when the install was chosen and not bought yet (the note's `neuroFluxTarget`, #222 review: an install counted on them installs them). An install keeps it (`Server/ServerHelpers.ts:224-237`).
  3. **NeuroFlux Governor,** a level at a time, while the money and a seller's reputation cover it.
  4. **The install** (`installAugmentations`, #164), once the faction state shows every purchase the Agent reported done.
     - Never an install of nothing (#213 re-review): what it would install is the faction state's queue and the purchases reported done it doesn't show yet, never one `augmentationNotQueued`. With none, the cycle is called off ("nothing queued to install"), a restarted brain's already asked-for install too.
     - It's queued after the owner's whole queue, through the gate (its guard: nothing before it undone; two medium snapshots; a save backup) and the reset note ([intents](#intents)).
     - Once it's asked for, nothing more is bought, so a purchase never restarts its gate's count.
     - An install the owner queued has the same id, so it goes once, as the owner's.

  Meanwhile:
  - the programs rule stands down, as an install loses the programs;
  - the controller's `augmentationReserve()` is Infinity;
  - a purchase reported done counts as queued until a faction state read shows it, so the next goes at once (the fast snapshot that reports it triggers the update);
  - if nothing is queued to install (the money went elsewhere, or every purchase was a false done), the cycle is called off: an `augmentationCycleCalledOff` event.
- **The reserve, for cloud servers** (A2, #194): `augmentationReserve()`.
  - Before the countdown: nothing, unless the rule would say install with `AUGMENTATION_RESERVE_LOOKAHEAD_MS` more income and both clocks that much later, A2's payback limit (15 minutes, decided in #213's review). Then the money the purchases it would count cost. With no income measured, nothing. A server bought now pays itself back within that, so holding money any sooner would cost the income the install waits for.
  - In the countdown: the counted purchases' money, held from home RAM too (`countdownReserve()`).
  - Committed: Infinity. With the switch off: 0.
  - `#reserveForOtherPurchase` holds back the larger of it and the program's or home RAM's reserve, so cloud purchases spend only what's above it.
  - While committed, no cloud server is bought or upgraded at all ("the install of augmentations chosen (cloud servers are lost at it)"), as no program is.
- **The money** is the medium snapshot's, less each purchase reported done in a fast snapshot taken after it, by the game's times (#213 review and re-review): the purchase after one goes at once, on the fast snapshot that reports it, before a newer medium snapshot shows the money spent. The Agent's round takes its snapshots before its intents, so a medium snapshot taken after the fast one shows the purchase. One reported done rounds after it was made (a page effector's) can be taken off a medium snapshot that already shows it, until the next: less money, the safe side.
- **The income's samples** are the game's own count since the install, so they're kept across the Agent's reconnects but for a gap (above); a reset starts them again.
- **The countdown** is the brain's alone, not stored: a restarted brain starts one again (the bars' clock it keeps).
- **A restarted brain** reads the commit, and whether the install was asked for (the note's `installing`): then it buys nothing more. An install out when it restarts is awaited from when it went out (the reset note's `sentAtMs`) until the Agent connects.
- **Purchases aren't irreversible intents** (core's `isIrreversibleIntent`), rightly: what's bought only takes effect at an install, which is the irreversible step, behind the gate. A purchase spends money, as a program's does.
- **Fail loudly:**
  - **Not queued:** a purchase the Agent reported done, which `NOT_QUEUED_AFTER_READS` (2) faction state reads since don't show queued. It still counts as queued for the plan, so it isn't asked for again (its done is already recorded, and it would be asked for forever). A skipped read doesn't count, and the first read may have been taken before the purchase. It's an `augmentationNotQueued` event, a log line ("augmentations: BitWire NOT QUEUED: …"), the dashboard's `augmentationNotQueued` alert, and a run report failure.
  - **No restart:** an install was out when the Agent disconnected, and no slow snapshot shows the reset 5 minutes later (`INSTALL_NOT_RESTARTED_AFTER_MS`). That's the dashboard's `installNotRestarted` alert. The run report fails an install sent with no reset seen within 5 minutes.
  - **Done, no reset** (#213 re-review): the Agent reported the install done (the game had nothing to install) and the next slow snapshot shows no reset. The faction state's queue isn't the game's: the cycle is called off, an `augmentationInstallNotReset` event and a log line ("INSTALL REPORTED DONE BUT THE GAME DIDN'T RESET"), the `installNotRestarted` alert at once ("install reported done but the game didn't reset"), and a run report failure. No other install is chosen until a reset or a brain restart.
  - A purchase or the install that fails is `intentStuck` after 5 tries, as for any intent.
  - **Install overdue** (#222): the run report fails a cycle 16 h online (`INSTALL_OVERDUE_ONLINE_MS`; the bar is 1 from 14 h) with no install chosen, naming its last counts. Nothing affordable in 16 h is reputation stuck, a failure too. Shown, not counted, with the switch off, or while The Red Pill's way held the rule.
- **Donations** (#225, [owner decision 53](../../docs/decisions/owner-decisions.md), under the Augmentations switch; the legacy faction manager's `canAffordWithDonation`, `faction-manager.js:546-549`, `:822-860`):
  - **Counted:** an augmentation no joined seller's reputation reaches, sold by a joined faction that takes donations with them unlocked (`donationTermsOf`, core's since #260), is in the set when the money covers its price and the donation for its missing reputation (core's `chooseAugmentationsToBuy` with `DonationTerms`): from the seller whose donation it raises least, one donation a faction, for the most reputation bought there. NeuroFlux Governor's levels likewise (core's `affordableCounts`). So the counts, the bars, the countdown's hold and the lookahead's reserve include the donations; the progress carries `byDonation` ("…(7 of 12 with NeuroFlux; 2 of them by donation)").
  - **Committed:** the note records each faction's donation (`donations`), and the install chosen event too. They go first, one faction at a time, as `donateToFaction { faction, amount, reputation }` (the amount from the faction's reputation now, core's `donationToReach`), each reported done and then shown by the faction state before anything else is asked for ("the faction state to show CyberSec's reputation after the donation"): the set is then what's reached, in buy order, as before. One the money no longer covers is passed over for the cycle, said in the log. Home's RAM never spends their money: they're made, or passed over, first.
  - **Shown:** each confirmed as an `augmentationDonated` event (the faction, the amount, its reputation before and after) and a log line; one the faction state shows before its done is reported is recorded then, once.
  - **Fail loudly:** a donation reported done that `NOT_QUEUED_AFTER_READS` faction state reads since don't show is `augmentationDonationFailed`: an event, a log line ("DONATION FAILED"), the dashboard's alert of that name, a run report failure ("donation failed"), and the cycle called off. And the run report fails **donations unused**: an augmentation within reach by a donation for 30 minutes online (`DONATIONS_UNUSED_ONLINE_MS`) while the brain's progress counted none by donation and it bought, donated and chose to install nothing.
  - **Daedalus's favour** (legacy `autopilot.js:920-931`; core's `augmentationEndgame` since #260): with Daedalus joined, its donations not unlocked, its reputation this cycle at what unlocks them at the next install, and The Red Pill's not reached, an install is chosen through the normal countdown, reason "Daedalus donations" ("Daedalus donations: its reputation this cycle unlocks its donations at the next install, so The Red Pill's reputation is bought, not earned"), if anything is to install; otherwise it's held, saying so. Not once 90% of The Red Pill's reputation is earned (legacy `work-for-factions.js:829`, `daedalusSpecialCheck`): A5's target for it is then The Red Pill's own (`redPillTarget`, shared by A5 and A6), and it's earned to the end. The install goes through without The Red Pill queued: the note's `reason` exempts it from #215's guard. Not in a BitNode where donations are unlocked from the start (BN8): there the next rule applies at once.
  - **The Red Pill bought:** once a seller's donations are unlocked, The Red Pill's way donates its missing reputation and installs for it ("The Red Pill") when the money covers the donation; until then its money is held back from cloud servers, home RAM and programs (`redPillHold()`), saying how much. Its donation is the note's first (`redPill`), the counts are budgeted without its money, and it's never passed over: its money gone, the cycle is called off and the next held for it.
- **The Red Pill and Daedalus first** (#215, [the World Daemon](#the-world-daemon)), overriding the count rule: with Daedalus's count and skill reached and its invitation not in, no install and $100b held back (from cloud servers and home RAM); joined, no install while The Red Pill is short of its reputation, but "Daedalus donations" once Daedalus's reputation unlocks its donations at the next install (#225, below); reached or queued, the install is chosen for it at once, with no countdown (`reason` "The Red Pill"), The Red Pill bought last. A hold calls a countdown off. Reported bought and never queued (`augmentationNotQueued`), it counts as owned, as R2 has it: the cycle is called off, and none is chosen without it. Committed on Daedalus's way, no install goes without The Red Pill queued, but for "Daedalus donations", an install for the favour (#225 review). Once it's installed, with the destroy wanted, no ordinary install is chosen. Each hold is logged as it starts.
- **Switched off:** nothing is bought or installed, the reserve is 0, and a cycle under way is called off. What's bought stays queued, for the owner.
  - The E2 tests' brains have it off (`effectors.e2.test.ts`).
  - So do the simulator suites that queue augmentations by hand: the install, destroy, backend and safe mode suites.

## Intents

M3's fourth slice ([#141](https://github.com/UnderMyBed/bitburner-agent/issues/141)): one-shot actions the Agent does at most once, sent in the desired state as `intents` ([protocol](../../docs/bridge/protocol.md#brain--agent), [`packages/ingame`](../ingame/README.md#intents)). Each is an action and its arguments, with an id made from them ("travel(Aevum)"): `buyTor`, `buyProgram`, `upgradeHomeRam`, `travel`, `joinFaction` (#147), `purchaseAugmentation` (#149), `buyServer` (#159), `backdoor` (#162), `installAugmentations` (#164), `destroyBitNode` (#175) and `upgradeServer` (#194) so far. Core validates them (`parseIntentRequest`) and says which are irreversible (`isIrreversibleIntent`).

- **Where they come from,** in this order:
  1. **The owner's manual queue** (`src/manual-intents.ts`), in the order added. It's queued on the dashboard, or with `POST /api/intents`, and kept in the store (`intents.manual`), so it survives restarts of the brain. Any action may be queued, irreversible ones too, with no confirmation (owner decision 36). A queued intent leaves the queue once the connected Agent reports it done, or when it's cancelled. Not when a snapshot shows its result (but for an install or a destroy, below): that can change again (a travel there and back would lose its last leg). Queued twice, it's queued once; one that isn't valid is refused with why; and the queue holds 95 at most, leaving room in the protocol's 100 for the purchase, the backdoor, the join, the augmentation's (#210) and the destroy (#215). The dashboard lists the queue even with no Agent connected, so it can be cancelled.
  2. **The purchase rules:** [the hacking programs](#the-hacking-programs) and [home RAM](#home-ram), one purchase at a time, the cheaper first; then [cloud servers](#cloud-servers) (#194), while neither is being bought. If the owner queued the same purchase, it goes once, as the owner's.
  3. **The augmentations** (#210, [above](#augmentations-and-the-reset)): a purchase after the purchase rules', and the install right after the owner's queue, through the gate. While an install is chosen, the programs and cloud servers stand down. Then the World Daemon's destroy (#215, [above](#the-world-daemon)), after the install, through the gate, unless the owner queued a destroy.
  4. **The backdoor** for a hacker faction (#195, [above](#backdoors-for-the-hacker-factions)), likewise.
  5. **The join** of a faction that invited the player (#203, [above](#factions-and-their-work)), likewise.
  6. **A travel for an invitation** (`travel`, #228, [above](#invitations-and-daedaluss-count)): Tian Di Hui's, or the chosen city group's, likewise.
- **When they go:** with the hack loop, in the one desired state. With the hack loop off, the manual queue goes before any snapshot: each intent checks the game first, so a stale one does nothing. While the brain holds, none go.
- **Irreversible ones** (R8, #147; so far, joining one of the six city factions, which bans its enemies, installing augmentations, #164, and destroying the BitNode, #175), the owner's or a rule's (#269: the brain's join of a city faction, judged after the owner's queue and the brain's destroy and install), go only past a gate (`src/irreversible-gate.ts`):
  1. the guard holds on two consecutive medium snapshots from the connected Agent, received after it was queued: for a join, none of the faction's enemies joined; for an install or a destroy (core's `resetsTheGame`), nothing queued before it undone (it resets the game, so what was queued before it was for this game; the augmentations queued can't be an install's guard, as no NS call shows them without Singularity); for a destroy, then, w0r1d_d43m0n's preconditions (core's `worldDaemonProblem`): among the medium snapshot's servers (reachable only once The Red Pill is installed), rooted there, and the hacking level at its required level, from the static snapshot (3000 times the BitNode's `WorldDaemonDifficulty`). The game also lets every Black Op done destroy it (`NetscriptFunctions/Singularity.ts:1176-1186`); the guard doesn't count that route, the conservative direction;
  2. then a save backup is asked for ([`backupNow`](#save-backups)), and the intent goes out once that backup succeeds.

  Around that:
  - **One at a time,** in the queue's order: the next one's guard is judged only once the first is done or cancelled, so two that conflict (Sector-12 and Chongqing) never go out together. One no longer first (since #269's review: an intent the owner queued goes ahead of a rule's join, even one out) goes back to counting: it's withdrawn, and goes out again only once first, past its guard and a new backup, never on a stale release or beside the new first.
  - **The guard fails closed:** a medium snapshot without the factions joined, or without the hacking level, or a static one without w0r1d_d43m0n's required level, holds the intent.
  - **Only the backup asked for counts:** a backup asked for before the count started again releases nothing.
  - **Out, it's still watched:** its guard failing withdraws it, and so does staying out 60 medium snapshots (about 10 minutes) without being done; it goes out again past a new backup, so the backup is never older than that when the game acts.
  - **A reset's guard on every update** (#271): nothing queued before it undone reads only the brain's queue, so it's judged on every update, not just on medium snapshots. The brain's own install and destroy come after the owner's queue, so anything the owner queues goes ahead of them: the reset is withdrawn at once, whether it was out or not ("not sent: held: travel(Aevum), queued before it, isn't done"), and once that intent is done or cancelled it needs its guard and a new backup again. Before #271 it stayed out until the next medium snapshot, up to about 10 s, beside the owner's intent, which the reset could then cut short.
  - **A failed backup** starts the count again, needing 6 medium snapshots (a minute) before the next.
  - A disconnect, a new Agent or a restarted brain starts every gate again.
  - A held intent doesn't hold up those queued after it, but for an install (#164) or a destroy (#175): what's queued after it waits until it's done, as it was queued for the game after the reset.
  - Each intent's view says why it isn't sent (`waitingFor`), and the dashboard shows it ("not sent: held: Sector-12's enemy Chongqing is joined", "not sent: waiting for installAugmentations() first: queued after an install, it's for the game after the reset", "not sent: held: hacking level 2500: w0r1d_d43m0n needs 3000").   - **Tested** (#269, #271) by `test/irreversible-intents.property.test.ts` (fast-check), with every rule on, and in some runs the brain's own install (#210) or destroy (#215) chosen: whatever the owner queues or cancels, the factions joined and invited, the save backups' answers, the Agent's reports and reconnects, every irreversible intent sent, the owner's, a rule's or the brain's own reset, has its guard holding (a reset's, nothing ahead of it in the queue), leaves its gate only on its own save backup answered saved, and goes out alone. The random properties shrink a failure, for at most 20 s (`interruptAfterTimeLimit`); the floor tests report one as found.
- **An install's or a destroy's done check** (#164, #175): it kills the Agent, so the one that sent it never reports it done, and a destroy can't be seen done in the game at all (another can follow). When the brain sends it, it notes the connected Agent's reset time (the slow snapshot's `lastAugReset` for an install, `lastNodeReset` for a destroy, which an install doesn't move); a slow snapshot with another one, from the next Agent, takes it off the queue (another, not only a later one: the game takes it from the clock, which can be set back, #167), so it isn't gated and backed up again for the new game. The note is kept in the store (`intents.resetSent`), so a brain restarted meanwhile still drops it on the reset: a destroy gated again in the next BitNode would wait for its requirements, then destroy that one too. Restarted before the reset, the same game's slow snapshot keeps it, and it's gated again. So that the note is always written, an install or a destroy past its gate goes out only once the connected Agent's slow snapshot has said the reset time ("not sent: waiting for the Agent's slow snapshot (the game's last reset), …").
- **Property tests** (#179, `test/desired-state.property.test.ts`, fast-check, 60 runs, under 1 s, each run on a store in memory, #279): a queue of every action (the joins with enemies and without, both resets), with the rules off or on, and any history after it: the owner queuing and cancelling, medium snapshots whose guards hold or fail, save backups that succeed or fail, the Agent's rounds reporting intents done or not, an install or a destroy done resetting the game (the brain up, or down across it so the next brain meets the reset game; the clock moved on, or set back, #167), slow snapshots with invitations, reconnects and a restarted brain. With the rules on, some runs have the brain's own install (#210) or destroy (#215) chosen, and each backup asked for must follow two consecutive medium snapshots with the guard holding, by the model's count. ## Work

M3's eighth slice ([#151](https://github.com/UnderMyBed/bitburner-agent/issues/151), owner decision 37): the brain's second activity for the Agent, the work the player does (`src/work.ts`, `src/desired-state.ts`).
- **What:** faction work, `{ faction, workType }` (hacking, field or security), or company work ([#153](https://github.com/UnderMyBed/bitburner-agent/issues/153)), `{ kind: "company", company, field }` (one of the game's companies, and one of its job fields: "Software", "Waiter", …), or a crime ([#156](https://github.com/UnderMyBed/bitburner-agent/issues/156)), `{ kind: "crime", crime }` (one of the game's 12), or a class ([#158](https://github.com/UnderMyBed/bitburner-agent/issues/158)), `{ kind: "class", location, classType }` (a university and a course, or a gym and a stat: "str", "def", "dex" or "agi"; `packages/core/src/classes.ts`), set on the dashboard (or `POST /api/work`) and kept in the store (`work.desired`), so it survives restarts of the brain. None set: [the brain's faction work](#factions-and-their-work) goes (#203), unless its switch is off; with neither, no `work` goes, and the Agent leaves the game's work alone.
- **Focus:** worked out by the brain, not set by the owner: focused for full gains, unless they come unfocused too: the Neuroreceptor Management Implant installed, as the connected Agent's slow snapshot says, or a part-time job (#153: Part-time Waiter, Part-time Employee; `Work/CompanyWork.tsx:36`). A class (#158) always goes unfocused: focus changes nothing for it (`Work/Formulas.ts:108-121`). Before that snapshot, focused, unless it's part-time or a class.
- **When it goes:** in the one desired state, once the connected Agent's slow snapshot has said whether the implant is in (so the focus never flips on a connect), and with the hack loop on, once its static and medium snapshots are in too. While the brain holds, none goes, and the Agent leaves the work as it is.
- **How it went:** the Agent's `work` outcome in the fast snapshot (converged, the problem, the backend), shown on the dashboard. Just after a change it may still be the last work's, until the next fast snapshot.
- **Promotions** ([#155](https://github.com/UnderMyBed/bitburner-agent/issues/155), owner decision 44): the Agent takes any later title of the company work's field the game offers, checking when the work starts and every 10 minutes ([packages/ingame](../ingame/README.md#work)); the brain chooses the company and field, not the title. The outcome's `promotion` (the latest, `{ company, from, to, gameTimeMs }`, read only if well-formed) is shown on the dashboard's Work row ("…: converged via ui; promoted from IT Intern to IT Analyst"), stored as a `workPromotion` event and logged ("the Agent took a promotion at Carmichael Security: IT Intern to IT Analyst"), once: the outcome carries it snapshot after snapshot, so one already stored, after a restart of the brain too, isn't again.

## The faction state

M4 phase A slice A4b ([#197](https://github.com/UnderMyBed/bitburner-agent/issues/197)): each joined faction's reputation and favour, the outstanding invitations and the queued augmentations, in each slow snapshot's `factions`, as the Agent reads them ([packages/ingame](../ingame/README.md#the-faction-state)). For the faction and augmentation choices ([A5](#factions-and-their-work), A6): `factionStateOf(slow)` in core gives the state only when the reading is well formed and was read; the desired-state controller keeps the latest slow snapshot whole, so it has them.
- **Unread is loud** (`src/faction-state.ts`), but a single miss isn't a failure: a slow snapshot whose reading has no state, with its problem, or whose `factions` isn't well formed (a bug), is stored as a `factionStateUnread` event (`{ backend, problem }`) and logged ("the faction state couldn't be read (ui): …"), once per change of problem, and `factionStateRead` once it's read again; after a restart of the brain, the last of those stored says where it was. The dashboard raises `factionStateUnread`, and the run report fails, only once 3 slow snapshots in a row are unread, as an intent is stuck only after its tries: a dialog flood or the owner acting mid-read misses one. What isn't unread: a reading skipped (no sidebar on the page, the BitVerse say), one read with the page not put back as found ("read, but the page wasn't put back as found", shown on the dashboard and counted in the report), and an older Agent's slow snapshot, which has no reading (a redeploy's old Agent sends one): "not read by this Agent", information only.
- **The simulator suite** (`test/faction-state.test.ts`): a fresh start with CyberSec joined at 1,000 reputation, Sector-12's invitation ($20m in Sector-12), three augmentations queued (NeuroFlux Governor twice) and BitWire installed, working for CyberSec, 3 virtual minutes: through `sim`, every slow snapshot has CyberSec's reputation rising, its favour, the invitation and the queue, as do the dashboard's status and the run report, which passes; through `singularity` (BN1, SF4.3), the same, from the first slow snapshot; through `ui` on the simulator's page, which renders no sidebar, skipped each time, not a problem, PASS; and through `ui` with its worker deleted from home, unread every time, one event, then the alert and the report's FAIL, never an empty state.

## Safe mode

M3's twelfth slice ([#160](https://github.com/UnderMyBed/bitburner-agent/issues/160), architecture §5.4): with the brain gone, the Agent keeps converging the hack loop and the work on the last desired state, never its intents, until its `ttlMs` passes ([packages/ingame](../ingame/README.md#safe-mode)).
- **The brain's part:** every state it sends carries `ttlMs`, `SAFE_MODE_TTL_MS` (12 hours, `src/desired-state.ts`), counted from when the Agent was last connected to it. Nothing in a state turns harmful with time alone (a reset, which does, drops it at once), and the loops and the work carry on after it anyway: it bounds how long a stopped brain's choices outlive it, and covers a night or a working day with the brain stopped or crashed for good. While the brain holds, the held state carries it too: it starts nothing new.
- **The dashboard:** nothing new. With the brain down there is no dashboard; back, it sends a fresh state, and the dialogs the Agent handled meanwhile arrive in its first fast snapshot.
- **The chaos suite** (`test/safe-mode.test.ts`), in an 8 GB fresh start in the simulator, the brain stopped with `stop()` (`test/helpers/brain-in-simulation.ts`: its connections closed, and every new one closed as it's made):
  - **The brain down for an hour, with a reload in the middle:** the file holds the hack loop and the work (faction work for Sector-12), never the queued join of CyberSec; a loop killed and the work switched by the owner are put back within a convergence, before and after the reload; the join is never tried while the brain is down (checked every 10 minutes of the Agent's log); the reloaded Agent's clock is the same 12 hours from the disconnect; the brain back tries the join again, with the loops and the work as they were.
  - **Past `ttlMs`** (5 minutes, set directly): a loop killed within it is put back; past it, the state is dropped, the file emptied, and a loop killed stays killed.
  - **A reset with no brain** (a new BitNode, `boot.js` standing in for the restart path): the kept state is dropped, never converged on: no loops, no work.
  - **Deployed again while the brain is down** (a new deployment written by hand, after the owner switched the work): the new deployment's Agent carries on from the file, its own loops in place of the old, the work put back.
  - **A brain that accepts the connection and never answers:** while the Agent waits for its welcome, safe mode goes on, and a killed loop is put back.

## Supervision

The brain keeps the game itself running, for unattended play ([#94](https://github.com/UnderMyBed/bitburner-agent/issues/94); architecture §10.2, R9). It's process management only: nothing touches the game's code or its save.

- **Only an E0 brain on Windows supervises** (Steam's game). A brain for a source build (E2), or one on another system, never launches or kills anything, and its dashboard shows supervision "off". Tests run the brain as E2 for that reason.
- **Setting up the game? Pause supervision on the dashboard first.** An E0 brain on Windows launches Bitburner within 30 s of starting. It kills and relaunches it if no Agent reports for about 5 minutes. That's always the case before the game's settings are made, before the first `run agent/boot.js`, and on a new save. Resume once the dashboard shows the Agent connected.
- **Every 30 s, unless paused or given up**, it looks, and waits are counted in checks, not by the clock. So the clock stepping (time sync, waking from sleep) can't make a healthy game look silent, or hide a frozen one:
  - **Not running** → launch it through Steam (`cmd /c start "" steam://rungameid/1812820`), as a player does. Cause: `notRunning`.
    - So starting the brain starts the game: after a reboot, `npm run brain` brings both back.
    - **After a launch it waits 10 checks (5 minutes) before doing anything else,** so Steam can start, log in or update the game. If the game still isn't running then, it launches again.
  - **Running, but no new heartbeat for 10 checks in a row** (the fast snapshot, every 2 s; about 5 minutes) → kill it (`taskkill /IM bitburner.exe /T /F`) and launch it. Cause: `silent`.
    - This covers a frozen page, and an Agent that died while the game runs: a reload brings it back through autoexec.
    - A heartbeat counts as new by being a new snapshot, not by its time.
    - At most the progress since the last autosave (60 s by default) is lost.
    - The heartbeat comes even when home is full and no worker can run, so a full home never looks silent.
    - If taskkill reports a failure but the game is gone anyway, it still launches.
  - **Grace:** silence counts only after 10 checks (5 minutes) since the brain started or supervision was resumed. After a launch, the 10 checks start once the launch's wait is over, so the earliest kill is 10 minutes after the launch (a brain restart or a resume in between starts a plain 10-check grace instead). That gives Steam time to start the game, and the Agent time to boot.
  - **Running** is what `tasklist /FI "IMAGENAME eq bitburner.exe" /FO CSV /NH` lists, matched by image name. Its "no tasks" message is in the system's language, so it isn't read. Any `bitburner.exe` counts, so don't run another copy of the game (a non-Steam download, say) alongside.
  - The three programs are run by their full path in System32, never through a shell's parsing.
  - The switch is read again just before anything is killed or launched, so a pause is never late.
- **At most 3 launches in any hour,** the first included. A 4th would mean a crash loop, so the supervisor gives up instead, which raises the dashboard's `supervisionGaveUp` alert.
  - It stays given up, across restarts of the brain, until you resume supervision on the dashboard. Resuming after a give-up starts the count afresh.
  - The count comes from the store, so a brain that keeps restarting can't get round it.
- **A check that fails** (a command that errors or times out after 30 s, or a switch setting it didn't write) is recorded once, when a run of failures starts. Ten failed checks in a row (5 minutes) give up, with the same alert (its text says which cause, with the last failure: #127), so a broken Steam link doesn't fail silently for ever.
- **Paused** (the dashboard's switch): nothing is launched or killed, so you can close the game on purpose, or set it up.
- **Recorded:**
  - each launch is a `relaunch` event, with its cause;
  - a give-up is a `supervisionGaveUp` event, with the cause and the launches in the last hour, or with the failure that kept happening;
  - the start of a run of failed checks is a `supervisionFailed` event, with the failure and the cause it was acting on.
- **Stopping the brain** stops the checks first, so the game isn't relaunched while the brain shuts down.
- **Config:** `steamAppId` (1812820, verified on the reference rig) and `gameExecutable` (`bitburner.exe`).
- **Checked on the reference rig** by M2's owner's check (game closed, Agent killed, paused), recorded on #94. Since owner decision 45 there's no manual check: a live run's relaunches, failed checks and give-ups show in [the run report](#the-run-report).

## The gap report

The evidence for M2's exit criterion, "live snapshots on Steam without gaps" (architecture §13). Since M3, a release's live run is read back with [the run report](#the-run-report) instead ([releasing](../../docs/releasing.md) step 2), whose health section has the same gap check:

```
npm run gaps -- --since 2026-10-27T00:00:00Z --until 2026-10-28T00:00:00Z
```

- **What it lists:** every interval between consecutive fast snapshots (the heartbeat, every 2 s) longer than the threshold, including from the window's start to the first snapshot and from the last one to its end. It also shows the count, the first and last snapshots, and the longest interval.
- **The page heap** over the same window, from the fast snapshots' `pageHeapUsedBytes`: the first and last values, the lowest and highest, and how many snapshots reported one, or "not reported" (E2 has none). Growth would show here first (architecture R10). It's for reading: it doesn't change the exit code.
- **What it proves:** that the Agent was alive. A fast snapshot counts even when its tiers are degraded (`game: null`, [degraded snapshots](../ingame/README.md#snapshots)); whether data arrived shows in each snapshot's `degradedTiers`.
- **Options:**
  - `--threshold-seconds`, default 6: three cadences. Exactly the threshold isn't a gap.
  - Times need a `Z` or an offset (`2026-10-27T00:00:00Z`): without one, JavaScript would read them as local time.
  - A window that ends before it starts (or a `--since` in the future) checks nothing, so it's an error (exit 2), never "no gaps".
  - It opens the store read-only, so it's safe while the brain runs.
  - `--environment`, default `E0`.
  - `--until`, default now.
- **Exit codes:** 0 with no gaps, 1 with gaps, 2 when it couldn't run.

## The run report

What a run did and what went wrong, from the store alone (#185, owner decision 45): the "analyse" step of build, test, run, analyse, in place of a manual smoke test. What each section says, and what a FAIL means, is in [docs/setup.md](../../docs/setup.md#after-a-run-the-run-report).

```
npm run report -- [--data-dir <dir>] [--since <ISO time>] [--until <ISO time>] [--environment E0] [--verbose]
```

- **Summaries by default, `--verbose` for the detail** (#245; `runReport`'s `verbose`): run #3's 12.4 h report was 3,237 lines, about 2,700 of them section 3's one intent, cloud server, augmentation, faction work choice or dialog each, and section 2's inferred target. #245's first round brought it to 846 lines and 85,219 characters, still over a GitHub comment's 65,536 (the release posts it as one, [releasing](../../docs/releasing.md)): the invitations log, the work's changes and the ui backdoors' routine second tries were most of the rest. Now each is summarised a line a cycle, so a run's default report grows with its cycles, not with how busy each was (about 1,100 characters a cycle, 2b's block most of it; the coordinator checks run #3's figure under 60,000); `--verbose` lists each line as before. The summaries:
  - **intents** (`intentLines`): counts by action (the id's name before its arguments) and outcome, the most first ("backdoor: 51 done (36 tried again while still at it)"), then each one not done, done with a problem, or tried again for something besides its worker still at it, in its `--verbose` line. A try that only found its worker still at it ("installing the backdoor on CSEC: about 40 s left", `ingame/src/workers/backdoor-standing.ts:36`; "its worker is still at it"; "its last worker is still running") is routine: a ui backdoor's first try starts it and returns. One tried again with nothing reported is listed, as why isn't known. An install or a destroy not done whose reset followed (#286) is done, counted "1 by the reset that followed, with no done record" and in its `--verbose` line "done: the reset followed, 0 tries; the reset seen by …". The reset kills the worker before it reports: an install's try counts only once its worker returns (`ingame/src/agent/intent-runner.ts:48-51`), which it never does, hence its 0 tries; and a destroy's worker never reports done (`ingame/src/page/destroy-page.ts:110`). Its reset is the one section 4 sees for an install (`AugmentationTimeline.resetSeenBetween`: a slow snapshot with another `lastAugReset`; a destroy's counts too, as it resets the cycle) and section 2 for a destroy (`BitNodeCycles.bitNodeSeenBetween`: another BitNode), after the intent's first record, within `RESET_FOLLOWED_WITHIN_MS` (5 minutes) of its last, and before the same id's next episode. A reset before it, or later, isn't its, nor is the window's first slow snapshot (nothing before it to change from; on either side, #286 review): an install or a destroy first seen before it is not done, "before the window's first slow snapshot: not judged", in the words section 4 uses for an install sent then (`BEFORE_FIRST_SLOW`). The next episode can't start before the reset's slow snapshot is in: the brain sends a reset intent only once the connected Agent's slow snapshot has shown the last reset (`#resetTimeAwaited`, `desired-state.ts:1103-1107`), so a reset is never put down to an install given again by the next Agent;
  - **cloud servers** (`cloudServerLines`): the fleet a line a cycle, its count and RAM before the cycle's first change and after its last, so a change of the fleet's total at most once a cycle ("BN1.1 1, … to …: none → 20 servers, 640 GB (20 bought, 20 upgraded, $35,200,000)"), then the total;
  - **work** (`workLines`): its changes a line a cycle, counted by state ("15 changes: not converged ×7, converged (ui) ×7, not converged (ui)"), and each change with a problem listed ("not converged (ui): a dialog the Agent leaves for the owner is open"). A new work wanted reads "not converged" with no problem until its first try (`ingame/src/agent/work.ts:44`), which is routine;
  - **dialogs** (`dialogLines`): counts by kind, an alert by its first 4 words (`ALERT_FIRST_WORDS`, so 3 Source-File alerts aren't lost among 105 messages), and each left blocking the page (section 4's failures);
  - **backdoors** (`backdoorSummaryLines`): a line a hacker faction's server however many resets: backdoored at the window's start or not, in how many cycles it was backdoored and how long after each cycle's start (the least and the most, and where; `BitNodeCycles.cycleStartAt`), not backdoored since a last reset, and its faction's invitations (run #3's lines were about 2,000 characters each, every reset in full);
  - **factions joined**: each faction's first join counted by its cycle ("11 factions, each first in: at the window's start: 2, BN1.1 1: 9");
  - **section 2's lists** (`describeListChange`): a first → last list of 100 characters or more (the installed augmentations, the purchased servers, the factions, …) as its counts and the names added and gone, six of each at most ("5 → 17 (+ …, and 6 more)", "25 (unchanged)"); shorter, in full;
  - **faction work** (`factionLines`): the choices a line a cycle, counted by work and faction, and the stops by reason;
  - **invitations** (`invitationLines` with a `cycleOf`): a line a cycle, the city group chosen, the travels by city, the holds, and the factions that invited; a hold with no invitation ("NOT INVITED …") or a phase this brain doesn't store is listed under it;
  - **augmentations** (`AugmentationTimeline.summaryLines`): a line a cycle, the set bought with NeuroFlux Governor's levels as one count and their price, the installs chosen and why, the donations by faction ("2 donations: $1,000,000,000 to CyberSec, $2,000,000,000 to NiteSec": the reason chosen can name another faction), and the installs sent; a donation not shown, or an install with no reset, is listed under its cycle all the same. The progress events and the installs seen are left out: 2b says how each cycle went and what it installed (the multipliers gained and the Agent's time away only with `--verbose`);
  - **the hack loop's target:** the batcher's targets from its health in the fast snapshots, each stretch of one, ended by another target, a reset, or no look naming it for more than the heartbeat's 6 s (the same target after one is another stretch); with no batcher health (an older store, or the hack loop alone), the inference, as with `--verbose`. Neither crosses a reset (`resetBetween`): 2b's estimate of the cycle's start on the brain's clock, or a `lastAugReset` between two snapshots' own game times, which no clock offset can move (an install or a destroy puts every server's money back, which run #3's report listed as all ~50 servers at each install).

  The cycles are 2b's (`BitNodeCycles.cycleLabelAt`: "BN1.1 2"; "before BN1.1 1" before the first; "the window" with none seen). **The checks don't change:** sections 4 to 6, every failure and warning line and the verdict are the same with `--verbose` or without (a test asserts it).
- **The window:** `--since` defaults to the newest `brainStarted` event, `--until` to now. Times need a `Z` or an offset, as for the gap report. The newest `brainStarted` includes the brain runner's own restart after a crash, so a run spanning a restart needs `--since`; section 1 notes a `brainStarted` in the 24 h before the window.
- **Over a thinned window** (#283, [thinning](#thinning)): section 1 notes how many fast and medium snapshots in the window are thinned, and up to when. The time checks read every snapshot, so the heartbeat's gaps, clock steps, page stalls, the page heap and the run's end are exact; everything else reads the whole snapshots, one a minute there. So its times there are within a minute, what came and went within one isn't seen (an intent done, a change of work, a dialog left blocking for seconds), and two checks that need readings closer than a minute aren't judged there: a backdoor overdue (it needs medium snapshots within 30 s of each other) and a batcher stuck on a poor target (looks within 6 s). The batcher not running for 3 fast snapshots in a row counts whole ones there, a minute apart. A gap's reload reads the install or destroy the Agent held from the stubs too. The batcher's target goes on across the thinned snapshots, so a stretch isn't cut a minute at a time. A clean run's report over thinned data has the same sections and verdict, and its failures still fail: tests show each, and the differences line by line.
- **What it reads** (nothing new is recorded): the fast, medium, slow and static snapshots and the events in the window (section 5 recomputes the hacking ceiling from them, #196), through `iterateSnapshotsInWindow` and `eventsInWindow`, and the hack loop's and the Augmentations switches (#222). The snapshots are folded one row at a time (a day's are hundreds of MB once parsed), and every read is in one read transaction (`readTransaction`). It opens the store read-only, so it's safe while the brain runs.
- **The checks** (`src/run-report.ts`), each a line under FAIL (or, for a warning, under WARN, #241):

## The campaign report

Clear time, cycles and installs per BitNode, per release, over the whole store: every run and restart in it (#290, architecture §7). It's the campaign's benchmark in place of community numbers, and it compares releases directly ("did v1.0.1 clear BN1.4 faster than v1.0.0?"). What it prints, for the owner, is in [docs/setup.md](../../docs/setup.md#the-campaign-report).

```
npm run campaign -- [--data-dir <dir>] [--environment E0]
```

- **Its own command**, not a flag of `npm run report` (#290's spec): the run report's window, `--verbose` and verdict don't apply to the whole store. It opens the store **read-only** (`TelemetryStore.openReadOnly`, as the run report's command does), so it's safe on the owner's store while the brain runs; a test runs it on a store file marked read-only and checks the file's bytes are unchanged. Exits 0 with the report, 2 when it couldn't run: no store, or no slow snapshot in the environment showing a BitNode (`resetInfo`).
- **What it reads: the slow snapshots and three kinds of event, never a medium or fast snapshot**: `brainStarted`, `augmentationInstallSent` (its `source`) and `bitNodeDestroySent` (`CAMPAIGN_EVENT_KINDS`, through `eventsInWindow`'s `kinds`), over all time, in one read transaction, the slow snapshots folded a row at a time. So however a store is thinned (#283) the report is the same, as long as the events and the slow snapshots are kept whole (the time online is built from the steps between slow snapshots). Each slow snapshot's payload is parsed whole for its `resetInfo`, about 525,000 a year at one a minute; a `json_extract` of `resetInfo` in the query is the fix if that's ever slow. A slow snapshot with no `resetInfo` to read is left out, and counted in the header.
- **Where each BitNode and cycle starts is the run report's detection** (`ResetDetection` in `src/cycle-report.ts`, #244): another `lastNodeReset` is another BitNode, another `lastAugReset` another cycle, each start by the brain's clock. A label played again (BN1.4 after SF1.3, a new game, or a save loaded) is numbered: "BN1.4 #2".
- **How a BitNode ended**, from the next one's start (`endingOf`):
  - a start before the BitNode's last look (its last slow snapshot's game time) is **a save loaded**, older or newer: never a destroy, and the BitNode it starts has its start unseen (its wall clock and time online are "≥", and it's never a clear of its own);
  - the Source-Files are compared from the BitNode's last look to the next one's first (`sourceFileChange`), leaving out any a `sourceFileOverrides` on either side hides (`ownedSF` shows an overridden one at its override, `NetscriptFunctions.ts:1491-1495`; set in the BitNode's options, `BitNodeUtils.ts:54-62`, `BitNodeAdvancedOptions.tsx`);
  - its Source-File gained a level, and no other changed: **destroyed** (`RedPill.tsx:62-63`, `giveSourceFile`); more than one level, or another Source-File rose too: **destroyed, BitNodes unseen before** the next (BitNodes played that the store didn't see: its destroy's time unknown, so its wall clock and time online go to its last look, the step to the next start isn't counted, and it's never a clear of its own); another rose and its own didn't: **BitNodes unseen before** the next;
  - at its Source-File's cap (level 3, any BitNode but 12, `RedPill.tsx:28`: no level to gain) with a `bitNodeDestroySent`: **destroyed (at the cap)**. Only the last destroy sent in the BitNode counts, and only within `RELOAD_LEAD_MS` (10 s) of its last look or after it: one with the BitNode's slow snapshots after it didn't happen then;
  - its own Source-File overridden on either side (its level doesn't say): the destroy sent, on the same rule, **destroyed (its Source-File overridden; the destroy sent)**, or else **unknown**;
  - a Source-File lost: **a new game** (a new player's `lastNodeReset` is when it began, `PlayerObject.ts:168`); also with no Source-File to lose, since b1t_flum3 needs one (`Programs.ts:29-33`, `BitNodeUtils.ts:21-25`);
  - otherwise **b1t_flum3**, which enters a BitNode with no Source-File (`RedPill.tsx:62`'s `isFlume`; `Programs.ts:306-322`, `Singularity.ts:1148`), or at the cap a destroy the brain didn't send;
  - the newest BitNode: "destroy sent …, the next BitNode not seen", or "not yet".
- **Time online** is the bars' clock's rule (`advanceOnlineClock`, #222) over a whole BitNode, keyed by its `lastNodeReset` (in the clock's `lastAugReset` field), not one cycle: the game's time between slow snapshots no more than 3 minutes apart (`AUGMENTATION_SLOW_GAP_MS`), from the BitNode's start (its `lastNodeReset`) to its end (the next one's, after a reset), installs and all. **What it leaves out is shown** (the "left out" column, and each Compared entry): an offline gap, or the brain or the Agent away, each step over 3 minutes, and the step from the start to the first look where the store saw the start. The game goes on offline (`engine.tsx:264-271`), so a release away more could look faster online. The wall clock (the brain's, from the start to the next BitNode's) counts it all.
- **Cycles and installs:** each `lastAugReset` a BitNode's slow snapshots show is a cycle, each one that isn't its `lastNodeReset` an install, each counted once. Another cycle whose `lastAugReset` was seen already, or is before the last look, is **a save loaded** (older, or a newer one gone back to), listed, not an install; an install's is the game's time at the install (`PlayerObjectGeneralMethods.ts:126`), after the last look. One edge: the PC's clock set back before an install makes its `lastAugReset` earlier than the last look, so that install reads as a save loaded (and the clock's step back isn't time online). "≥" marks a lower bound: the cycles and installs of a BitNode whose first slow snapshot showed an install already.
- **By hand:** an install with no `augmentationInstallSent` from the brain's own rule (`source` "brain") in the cycle it ended: one from your queue (`source` "manual"), the game's Install button, or a Soft Reset (`ui/GameRoot.tsx:297-301`). Counted in the installs ("3 (1 by hand)"); a BitNode with one is never a clear of its own.
- **A release is the brain's**: the stored release (`<git describe>+<the Agent's deployment>`) before its "+" (`brainReleaseOf`), since the deployment changes with any rebuild. A brain run from an untagged or dirty checkout is its own release (`v1.0.0-4-gabc1234`, `…-dirty`): running from `main` splits a BitNode at every pull, so a clear to compare is a tagged release's. Each step of time online is the release of the slow snapshot that ends it, so the step across a change of release is the new one's (a BitNode's start, its first's; its end, its last's); an install is the release of the slow snapshot before it.
- **What it prints:** a header (the store's first and last record read, the brain starts, the releases); **a row per BitNode** (its start, how it ended, the wall clock, the time online and the time left out to its end, or so far, the cycles, the installs and those by hand, the augmentations installed at its last look, the brain starts in it, its releases), then each one's Source-Files as entered, time online by release, augmentations by name, and saves loaded; **a row per release and BitNode it played** (its time online there, the cycles it had a slow snapshot in, the installs it made, and whether it destroyed it: "a clear of its own" where it played the BitNode, the store seeing it from its start and first cycle to its destroy, with no save loaded in it ("yes, with a save loaded in it") and every install the brain's, with the clear time); and **compared**: each BitNode (number and level) two releases or more cleared on their own, the fastest online first, each with its time left out and the Source-Files it was entered with (the comparison is by label only: the other Source-Files and the BitNode's options aren't matched).
- **Another release only at the start** (`STARTER_ALLOWANCE_MS`, 5 minutes; proposed owner decision 61): a release that played a BitNode only before the one that went on first did, with no install and at most 5 minutes online, leaves the other a clear of its own, its share printed ("a clear of its own (v0.2.0-53-g7c741cc's first 2 min 3 s)", in the Compared entry too). A brain upgraded just after a destroy is the case: the real store's BN1.3 (2 min 3 s of the release before, then 614978a's 12 h 34 min). Any more, and the BitNode is "played with … too".
- **Tests:** `test/campaign-report.test.ts` builds a campaign: BN1.1 begun two days before the store, across a brain restart onto another deployment and a 2-hour offline gap, with an install from your queue; BN1.2 played by two releases, the owner upgrading as an install reloads; BN1.3 and BN1.4 cleared by one; BN1.4 again by another (compared), each destroy at SF1's cap known by its `bitNodeDestroySent`; a third BN1.4 with a save loaded and a destroy sent; and the same campaign thinned (no fast snapshots, a medium one a minute), and the full store thinned by #283's own `thinStore` (its stubs), each of whose reports must be the same text. Then: a fresh save's BitNode from its start; an older BitNode's save loaded; saves within one BitNode and across BitNodes, back to an older one and then to the newer; a release changed mid-cycle; b1t_flum3 (with a destroy sent below the cap), a new game, a BitNode with no Source-File before it, BitNodes unseen (SF1 from none to 3, another Source-File rising), a destroy at the cap sent too early and none after, and BN12's uncapped Source-File; Source-File overrides on another Source-File and on the BitNode's own (with and without a destroy sent); a save loaded in a BitNode stopping a clear; another release at a BitNode's start, within and over the 5 minutes; the brain away across a destroy; installs by hand; a slow snapshot with no `resetInfo`; a BitNode begun before the store; and the command's exit codes and its read-only open.

## The lockstep driver

`SimulatedGame` (`src/simulated-game.ts`) runs a brain against a simulation ([ADR 0012](../../docs/decisions/0012-simulator-network-in-lockstep.md)). Every brain-plus-simulator test uses it; the live brain never loads it.

```ts
const simulation = await Simulation.start({ …, network: { listenUrls: ["ws://127.0.0.1:12526"] } });
const game = await SimulatedGame.create({ simulation, stepMs: 100 });
const channel = new ControlChannel({ token, clock: game.clock });
game.listen("ws://127.0.0.1:12526", (connection) => channel.accept(connection));
await game.run(60_000);   // virtual ms
await game.runUntil(() => channel.connectedAgent() !== null, 10_000);   // or fail after 10 virtual s
```

- **Each step:**
  1. the brain's queued frames and closes go to the page;
  2. the simulation advances one step;
  3. what the page's sockets did comes back in order, each handed to the brain at its own virtual time, with the brain's timers fired in between;
  4. the brain's clock moves to the simulation's time.
- **Determinism:** the same seed and step size give the same run, however long the brain's work takes in real time. Tests check it with a deliberately slow brain.
  - **The brain's handlers must be synchronous.** A batch of frames is handed over without yielding, so the continuation of an `await` on real I/O would land in whichever step real time put it in. Awaiting only replies that come through the driver is fine, as the deployer does.
- **Closes:**
  - A connection the brain closes stops carrying frames at once, but is reported closed only once the close reaches the page (the next step), as a live socket reports it after the closing handshake.
  - A close by the page is reported at the virtual time it happened.
- **Fail fast:**
  - Steps can't overlap: await each one.
  - A reload can't happen mid-step.
  - A page socket to a URL nothing listens on fails the step, once the whole batch has been handled.
- **The brain's clock** takes delays as Node does: under 1 ms, or not a number, waits 1 ms, so a timer that re-arms itself can't spin.
- **Fix the step size per test:** the brain's replies reach the page at the start of the next step, so the step size is part of what makes a run.
- **Waiting (`runUntil`):** steps until a condition holds, checked before each step, and fails once more than the given virtual time has passed.
- **Faults (`deliveredCopies`):** a test can say how many copies of each frame from the page reach the brain: 0 drops it, 2 duplicates it, both copies back to back.
  - The function is called once per frame, in order, so a seeded one gives a reproducible run.
  - It isn't asked about frames on a connection the brain has already closed: the brain would discard them anyway.
  - An answer that isn't a whole number of copies fails the step.
- **Reloads (`replaceSimulation`):** for a save loaded into a new simulation; start it with the same `network.listenUrls`.
  - Every socket of the old page closes at once, as a reload closes them, and frames still queued for it are dropped.
  - The steps then drive the new simulation, and the brain stays as it was.
  - The brain's clock never goes back: if the save's time is a moment behind it, the clock waits for the reloaded game to catch up.

## The skeleton suite

`test/skeleton.test.ts` is M2's exit criterion in the simulator (environment E1): "connect, snapshot, reload, reconnect, Agent RAM in an 8 GB fresh start" ([architecture §13](../../docs/architecture.md#13-milestones)). It runs on every PR, in about 25 s in CI, against a budget of 60 s.

- **What runs:** the brain is wired like `main.ts` (`test/helpers/brain-in-simulation.ts`): its control channel, deployer, store and save backups, in `main.ts`'s order (the hack loop aside: it has [its own suite](#the-hack-loop)), with the deployer and the backups sharing the game's RFA connection. The game deploys through its own Remote File API client, and the built Agent and workers play their part. Everything is on the lockstep driver at a fixed 100 ms step. `main.ts`'s own wiring, on real sockets, is tested by `brain-process.test.ts`.
- **The start:** a new game with 8 GB of home RAM, the tutorial skipped, and settings naming the brain's Remote File API and running `agent/boot.js` on autoexec. The brain deploys; the one-time `run agent/boot.js` brings the Agent up.

| Scenario | What it shows |
|---|---|
| 8 GB fresh start | For 10 virtual minutes every tier arrives in the right number, each its period apart. Home never holds more than the Agent and one worker. The store holds every snapshot exactly once, numbered with none missed, and the gap report finds no gap. A save backup is taken beside the deploy, on the same connection |
| Reload | The game's save, loaded into a new simulation, brings the Agent back through autoexec alone: the Agent is a temporary script, so the save doesn't hold it. It's a new session, from the same deployment, and it sends a full snapshot. The reloaded game's RFA client reconnects, nothing is deployed again, and a new backup is taken |
| Reconnect | The brain drops the connection. The same Agent session comes back after its first backoff (1 s) with a full snapshot, its numbering carrying on, and there's no gap |
| The Agent stopped for 30 s | The gap report finds exactly that one gap |
| Faults on the wire | For 5 virtual minutes, snapshot frames are dropped (30%) and duplicated (15%) at random, seeded, and three heartbeats in a row are always dropped. Every snapshot that got through is stored once, and each records how many of its tier were dropped since the one stored before it. The gap report finds the gaps the drops made and no others |
| Determinism | The faulty run, a minute long, run twice with the same seed and step, stores identical rows and events, timestamps included |

- **Home's RAM:** a snapshot worker starts and exits within one timer, so checking between steps would never see it. The suite reads the simulator's `homePeak` instead, which is taken as RAM in use and the script count change. Home must have run exactly two scripts at most (the Agent and a worker, which also shows a worker ran), and used at most the RAM of the Agent plus the largest worker, by the game's own figures.
- **Faults are on snapshot frames from the page only.** Over a WebSocket a frame can't be lost or repeated while the connection stays up, so the faults are there to try the store and the gap report, which only snapshots reach. A lost hello is the hello timeout's case, which the control channel's own tests cover, as they cover a duplicate that arrives late.
- **What it doesn't model:** a reload here loads a save taken that moment; a real one loads the last save, which may be older. The old page's sockets also close before the new Agent says hello. E2's skeleton covers that, with the game's real autosave ([`packages/e2`](../e2/README.md#the-skeleton-on-e2)).
